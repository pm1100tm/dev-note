# Claude Code 잘 사용하는 방법

Claude Code는 질문에 답하고 기다리는 챗봇이 아니라, 파일을 읽고 명령을 실행하고 코드를 변경하면서 스스로
문제를 풀어 가는 에이전트입니다.

**그래서 "무엇을 물어볼까"보다 "어떤 조건에서 일하게 할까"가 결과를 더 크게 좌우합니다.**

이 문서는 Claude Code를 설치하고 로그인한 다음 단계로, 매일 사용할 때 결과 품질을 높이는 습관과 설정을
정리합니다. 설치는 [Claude Code CLI 설치와 로그인](claude_001_install.md)을
참고합니다.

> 이 문서는 2026-10-13에
> [Claude Code 공식 Best practices](https://code.claude.com/docs/en/best-practices)와
> [Common workflows](https://code.claude.com/docs/en/common-workflows),
> [CLAUDE.md 문서](https://code.claude.com/docs/en/memory)를 기준으로
> 확인했습니다. 명령어, 단축키, 기본 권한 모드는 버전에 따라 바뀔 수 있습니다.

## 가장 중요한 제약: 컨텍스트 창

컨텍스트 창(context window)은 Claude가 한 세션에서 기억하는 작업 공간입니다. 내가 보낸 메시지뿐
아니라 Claude가 읽은 파일, 실행한 명령의 출력까지 모두 이 공간을 차지합니다.

디버깅 한 번이나 코드베이스 탐색 한 번에도 수만 토큰이 쌓일 수 있고, 컨텍스트가 가득 찰수록 앞에서 준 지시를
잊거나 실수가 늘어납니다. 아래에서 소개하는 방법 대부분은 결국 다음 두 가지로 정리됩니다.

- 필요한 정보는 정확하게, 필요 없는 정보는 적게 넣습니다.
- Claude가 결과를 스스로 확인할 수 있게 만들어, 내가 매번 검토자가 되지 않게 합니다.

세션 안에서 지금 무엇이 컨텍스트를 차지하는지는 `/context`로 확인할 수 있습니다.

## 스스로 검증할 수단을 함께 주기

Claude는 "작업이 끝난 것처럼 보이면" 멈춥니다. 테스트나 빌드처럼 성공과 실패를 알려 주는 신호가 없으면,
실수를 발견하는 역할은 전부 사람에게 돌아옵니다. 실행 가능한 확인 방법을 주면 Claude가 작업, 확인, 수정을
반복하며 스스로 마무리합니다.

| 전략                    | 나쁜 예                         | 좋은 예                                                                                                        |
| ----------------------- | ------------------------------- | -------------------------------------------------------------------------------------------------------------- |
| 검증 기준 제시          | "이메일 검증 함수 만들어 줘"    | "`validateEmail` 함수를 작성해 줘. `user@example.com`은 true, `invalid`는 false야. 구현 후 테스트를 실행해 줘" |
| UI 변경을 화면으로 확인 | "대시보드를 더 보기 좋게 해 줘" | "[스크린샷 첨부] 이 디자인대로 구현하고, 결과 화면을 캡처해 원본과 차이를 비교한 뒤 고쳐 줘"                   |
| 증상이 아닌 원인 해결   | "빌드가 실패해"                 | "빌드가 [오류 내용]으로 실패해. 오류를 숨기지 말고 원인을 고친 뒤 빌드 성공까지 확인해 줘"                     |

확인 방법은 테스트, 빌드 종료 코드, 린터, 출력 비교 스크립트처럼 결과를 대화 안에서 읽을 수 있는 것이면
됩니다. 또한 "성공했다"는 말 대신 실행한 명령과 출력, 스크린샷 같은 근거를 보여 달라고 요청하면 검토가
빨라집니다.

## 탐색 → 계획 → 구현 → 커밋 순서로 진행하기

바로 코드를 쓰게 하면 엉뚱한 문제를 푸는 코드가 나올 수 있습니다. 조사와 계획을 구현과 분리하려면 plan
mode를 사용합니다.

### 탐색과 계획: plan mode

세션 중 `Shift+Tab`을 눌러 상태 표시줄에 `⏸ plan mode on`이 보이게 하거나, 처음부터
plan mode로 시작합니다. 이 모드에서는 파일을 읽고 질문에 답하지만 파일을 변경하지 않습니다.

```shell
claude --permission-mode plan
```

```shell
src/auth를 읽고 세션과 로그인을 어떻게 처리하는지 파악해 줘.
Google OAuth를 추가하려면 어떤 파일을 바꿔야 하는지 계획을 세워 줘.
```

계획이 나오면 `Ctrl+G`로 텍스트 편집기에서 계획을 직접 고칠 수 있습니다.

### 구현과 커밋

계획을 승인하거나 `Shift+Tab`으로 plan mode를 벗어난 뒤 구현을 요청합니다. 이때도 검증 방법을
같이 줍니다.

```shell
계획대로 OAuth 흐름을 구현해 줘. 콜백 핸들러 테스트를 작성하고,
테스트를 실행해서 실패하는 부분을 고쳐 줘.
```

### 계획을 생략해도 되는 경우

오타 수정, 로그 한 줄 추가, 변수 이름 변경처럼 범위가 명확한 작업은 바로 요청하는 편이 빠릅니다. 공식 문서는
"변경 내용을 한 문장으로 설명할 수 있다면 계획을 생략하라"고 안내합니다. 반대로 접근 방식이 불확실하거나, 여러
파일을 바꾸거나, 익숙하지 않은 코드일 때 계획의 효과가 큽니다.

## 구체적으로 요청하기

Claude는 의도를 어느 정도 추론하지만 내 머릿속을 읽지는 못합니다. 파일, 상황, 제약, 참고할 기존 패턴을
알려 줄수록 수정 요청이 줄어듭니다.

| 전략           | 나쁜 예                      | 좋은 예                                                                                                  |
| -------------- | ---------------------------- | -------------------------------------------------------------------------------------------------------- |
| 범위 지정      | "foo.py 테스트 추가해 줘"    | "foo.py에서 로그아웃 상태의 엣지 케이스 테스트를 작성해 줘. mock은 쓰지 마"                              |
| 근거 위치 안내 | "이 API는 왜 이렇게 생겼어?" | "`ExecutionFactory`의 git 이력을 보고 API가 이렇게 된 과정을 요약해 줘"                                  |
| 기존 패턴 참조 | "달력 위젯 추가해 줘"        | "홈 화면의 기존 위젯 구현 방식을 보고, `HotDogWidget.php`를 참고해 같은 패턴으로 만들어 줘"              |
| 증상 설명      | "로그인 버그 고쳐 줘"        | "세션 만료 후 로그인이 실패해. `src/auth/`의 토큰 갱신을 확인하고, 재현 테스트를 먼저 작성한 뒤 고쳐 줘" |

탐색 단계에서는 "이 파일에서 개선할 점이 있을까?"처럼 열린 질문도 유용합니다. 내가 미처 생각하지 못한 부분을
발견할 수 있기 때문입니다.

### 풍부한 자료를 함께 넘기기

- `@` 뒤에 경로를 쓰면 파일 내용을 바로 대화에 포함합니다. 예를 들어
  `@src/utils/auth.js의 로직을 설명해 줘`처럼 요청합니다.
- 스크린샷은 드래그하거나 `Ctrl+V`로 붙여 넣습니다. Windows와 WSL은 `Alt+V`를 사용합니다.
- 문서나 API 레퍼런스는 URL로 알려 줍니다.
- 로그처럼 긴 내용은 파이프로 넘길 수 있습니다.

```shell
cat error.log | claude -p "이 오류를 설명해 줘"
```

### 큰 기능은 인터뷰부터 받기

요구 사항이 아직 흐릿한 큰 기능은 Claude가 나를 인터뷰하도록 시키고, 그 결과를 명세 파일로 남긴 뒤 **새
세션**에서 구현하면 효과적입니다. `[간단한 설명]`은 만들 기능으로 바꿔서 사용합니다.

```shell
[간단한 설명]을 만들고 싶어. AskUserQuestion 도구로 나를 자세히 인터뷰해 줘.
기술 구현, UI/UX, 엣지 케이스, 트레이드오프를 물어보고,
뻔한 질문 말고 내가 놓쳤을 어려운 부분을 파고들어 줘.
다 끝나면 완성된 명세를 SPEC.md로 작성해 줘.
```

## CLAUDE.md로 프로젝트 규칙 알려 주기

`CLAUDE.md`는 Claude가 매 세션 시작 시 읽는 지침 파일입니다. 코드만 보고는 알 수 없는 빌드
명령, 코드 스타일, 작업 규칙을 적어 둡니다. 프로젝트 루트에서 `/init`을 실행하면 현재 구조를 바탕으로
초안을 만들어 줍니다.

### 파일 위치

| 범위      | 위치                                     | 용도                                           |
| --------- | ---------------------------------------- | ---------------------------------------------- |
| 사용자    | `~/.claude/CLAUDE.md`                    | 모든 프로젝트에 적용할 개인 선호               |
| 프로젝트  | `./CLAUDE.md` 또는 `./.claude/CLAUDE.md` | git으로 팀과 공유하는 규칙                     |
| 로컬      | `./CLAUDE.local.md`                      | 나만 쓰는 프로젝트 설정, `.gitignore`에 추가   |
| 규칙 분리 | `.claude/rules/*.md`                     | 주제별 규칙, `paths`로 특정 파일에만 적용 가능 |

상위 디렉터리의 `CLAUDE.md`는 시작할 때 함께 읽고, 하위 디렉터리의 파일은 Claude가 그 디렉터리의
파일을 다룰 때 읽습니다. 파일 안에서 `@path/to/file` 형식으로 다른 파일을 가져올 수도 있습니다.

> 이 저장소처럼 `AGENTS.md`만 있고 `CLAUDE.md`가 없으면, Claude Code v2.1.277
> 이상은 `AGENTS.md`를 프로젝트 지침으로 읽습니다. `CLAUDE.md`나 `CLAUDE.local.md`를
> 추가하면 기본 설정에서는 `AGENTS.md`를 읽지 않으므로, 함께 쓰려면 `CLAUDE.md`에서
> `@AGENTS.md`로 가져옵니다. 자세한 조건은
> [공식 문서의 AGENTS.md 절](https://code.claude.com/docs/en/memory#agents-md)을
> 확인합니다.

### 무엇을 적고 무엇을 뺄까

| 넣을 내용                            | 뺄 내용                                  |
| ------------------------------------ | ---------------------------------------- |
| Claude가 추측할 수 없는 실행 명령    | 코드를 읽으면 알 수 있는 내용            |
| 기본 관례와 다른 코드 스타일         | 언어의 표준 관례                         |
| 테스트 방법과 선호하는 테스트 실행기 | 자세한 API 문서(링크로 대체)             |
| 브랜치 이름, PR 규칙                 | 자주 바뀌는 정보                         |
| 프로젝트 고유의 설계 결정            | 긴 설명이나 튜토리얼                     |
| 필수 환경 변수 같은 개발 환경 특이점 | 파일별 설명                              |
| 겉으로 드러나지 않는 함정            | "깨끗한 코드를 작성할 것" 같은 당연한 말 |

```markdown
# Code style

- import/export(ES modules)를 사용하고 require(CommonJS)는 쓰지 않는다

# Workflow

- 여러 파일을 수정한 뒤에는 타입 체크를 실행한다
- 전체 테스트보다 관련 테스트만 우선 실행한다
```

### 짧게 유지하기

`CLAUDE.md`가 길면 중요한 규칙이 묻혀 오히려 무시됩니다. 공식 문서는 파일당 200줄 미만을 권장하고,
각 줄마다 "이 줄을 지우면 Claude가 실수할까?"를 따져 보라고 안내합니다. 가끔만 필요한 지식은 아래의
스킬로 분리하고, 반드시 지켜야 하는 동작은 훅으로 강제하는 편이 낫습니다.

## 권한 모드 이해하기

Claude Code는 파일 수정, Bash 명령, MCP 도구 실행 전에 권한을 확인합니다. 매번 승인하다 보면
열 번째쯤부터는 검토 없이 누르게 되므로, 신뢰하는 작업은 미리 허용하는 편이 안전하고 빠릅니다.

- `/permissions`: `npm run lint`, `git commit`처럼 안전한 명령을 허용 목록에
  추가합니다.
- `/sandbox`: 운영체제 수준에서 파일과 네트워크 접근을 제한한 샌드박스 안에서 명령을 묻지 않고 실행하게
  합니다.
- auto mode: 별도 분류 모델이 위험해 보이는 동작만 막고 나머지는 진행합니다. 공식 문서 기준으로
  v2.1.283 이상의 대화형 터미널과 VS Code 세션에서는 기본 시작 모드입니다.

권한 설정은 저장소와 시스템에 대한 접근 범위를 바꾸므로, 회사 저장소에서는 팀의 보안 정책을 먼저 확인합니다.
자세한 내용은 공식 문서의
[Permission modes](https://code.claude.com/docs/en/permission-modes)를
참고합니다.

## 확장 기능 고르기

| 기능         | 위치·명령                         | 언제 쓰나                                                            |
| ------------ | --------------------------------- | -------------------------------------------------------------------- |
| CLI 도구     | `gh`, `aws`, `gcloud` 등          | 외부 서비스와 상호작용할 때 가장 컨텍스트 효율이 좋음                |
| MCP 서버     | `claude mcp add`                  | Notion, Figma, DB처럼 CLI가 없는 도구를 연결할 때                    |
| 스킬(Skill)  | `.claude/skills/<이름>/SKILL.md`  | 필요할 때만 불러오는 도메인 지식, `/이름`으로 실행하는 반복 절차     |
| 서브에이전트 | `.claude/agents/<이름>.md`        | 많은 파일을 읽는 조사, 보안 리뷰처럼 독립된 컨텍스트가 필요한 작업   |
| 훅(Hook)     | `.claude/settings.json`, `/hooks` | 예외 없이 매번 실행해야 하는 동작(편집 후 lint, 특정 폴더 쓰기 차단) |
| 플러그인     | `/plugin`                         | 스킬, 훅, 서브에이전트, MCP를 묶어서 설치할 때                       |

`CLAUDE.md`의 지시는 권고에 가깝고, 훅은 스크립트로 실행되므로 결정적으로 동작합니다. "항상 지켜야
하는데 자꾸 빠뜨리는 규칙"은 훅으로 옮기는 것을 고려합니다. 훅도 Claude에게 작성을 맡길 수 있습니다.

```shell
파일을 수정할 때마다 eslint를 실행하는 훅을 만들어 줘.
```

### 일찍, 자주 방향 바로잡기

| 동작                       | 효과                                                                          |
| -------------------------- | ----------------------------------------------------------------------------- |
| `Esc`                      | 진행 중인 작업을 멈춥니다. 컨텍스트는 유지되므로 바로 방향을 바꿀 수 있습니다 |
| `Esc` 두 번 또는 `/rewind` | 체크포인트 메뉴를 열어 대화, 코드, 또는 둘 다 이전 상태로 되돌립니다          |
| `/clear`                   | 컨텍스트를 완전히 비웁니다. 관련 없는 작업으로 넘어갈 때 사용합니다           |
| `/compact <지시>`          | 대화를 요약해 공간을 확보합니다. 예: `/compact API 변경 사항 위주로`          |
| `/btw`                     | 대화 기록에 남지 않는 곁가지 질문을 합니다                                    |

같은 문제로 두 번 넘게 수정을 요청했다면 컨텍스트가 실패한 시도로 가득 찬 상태입니다. 이때는 `/clear` 후
배운 점을 반영한 더 구체적인 프롬프트로 다시 시작하는 편이 대부분 더 낫습니다.

> 체크포인트는 Claude의 파일 편집 도구로 바꾼 내용만 추적합니다. Bash 명령이나 외부 프로세스로 바꾼
> 내용은 되돌릴 수 없으므로 git을 대신하지 않습니다.

### 조사는 서브에이전트에 맡기기

조사 과정에서 읽은 파일은 모두 메인 컨텍스트를 차지합니다. 서브에이전트는 별도 컨텍스트에서 탐색하고 요약만
돌려주므로, 메인 대화를 구현에 집중시킬 수 있습니다.

```shell
서브에이전트를 사용해서 인증 시스템이 토큰 갱신을 어떻게 처리하는지,
재사용할 만한 OAuth 유틸리티가 있는지 조사해 줘.
```

구현이 끝난 뒤 서브에이전트에게 diff를 리뷰시키면, 코드를 작성한 맥락에 치우치지 않은 시각으로 점검할 수
있습니다. 다만 리뷰어는 무언가를 찾도록 요청받았기 때문에 사소한 지적도 내놓기 쉽습니다. 정확성과 요구 사항에
영향을 주는 문제만 보고하도록 범위를 정해 줍니다.

### 세션 이어 가기

대화는 로컬에 저장되므로 여러 번에 걸친 작업도 처음부터 다시 설명할 필요가 없습니다.

```shell
# 현재 디렉터리의 가장 최근 세션 이어 가기
claude --continue

# 목록에서 골라서 이어 가기
claude --resume
```

세션 안에서는 `/resume`으로 다른 세션을 고르고, `/rename`으로 `oauth-migration`처럼
알아보기 쉬운 이름을 붙여 브랜치처럼 관리할 수 있습니다.

## 자동화와 병렬 작업

### 비대화형 모드

`claude -p`는 대화창 없이 한 번 실행하고 결과를 출력합니다. CI, pre-commit 훅, 스크립트에서
사용합니다.

```shell
# 일회성 질문
claude -p "이 프로젝트가 하는 일을 설명해 줘"

# 스크립트에서 파싱할 JSON 출력
claude -p "모든 API 엔드포인트를 나열해 줘" --output-format json

# 다른 명령의 출력을 입력으로 사용
git log --oneline -20 | claude -p "최근 커밋을 요약해 줘"
```

무인 실행에서는 `--allowedTools`로 필요한 도구만 미리 허용하고, 그 밖의 승인 요청은
`--permission-mode dontAsk`로 거부하게 할 수 있습니다. 여러 파일에 반복 적용할 때는
2~3개 파일로 먼저 시험해 프롬프트를 다듬은 뒤 전체에 적용합니다.

### worktree로 병렬 세션 실행

git worktree는 같은 저장소를 브랜치별로 별도 폴더에 체크아웃하는 기능입니다. 세션마다 다른 worktree를
쓰면 동시에 수정해도 서로 충돌하지 않습니다. 저장소에 커밋이 하나 이상 있어야 합니다.

```shell
claude --worktree feature-auth
```

다른 터미널에서 다른 이름으로 실행하면 독립된 세션이 하나 더 생깁니다. 한 세션이 구현하고 다른 세션이 새
컨텍스트에서 리뷰하는 Writer/Reviewer 방식도 이렇게 구성할 수 있습니다.

## 자주 하는 실수

| 실수             | 증상                                                  | 해결                                                    |
| ---------------- | ----------------------------------------------------- | ------------------------------------------------------- |
| 잡동사니 세션    | 관련 없는 작업을 한 세션에서 오가며 컨텍스트가 뒤섞임 | 작업이 바뀌면 `/clear`                                  |
| 반복 수정        | 수정 요청을 거듭해도 계속 틀림                        | 두 번 실패하면 `/clear` 후 더 나은 첫 프롬프트로 재시작 |
| 비대한 CLAUDE.md | 규칙이 많아 중요한 규칙이 무시됨                      | 과감히 줄이고, 꼭 필요한 동작은 훅으로 전환             |
| 검증 없는 신뢰   | 그럴듯하지만 엣지 케이스를 놓친 구현                  | 테스트, 스크립트, 스크린샷으로 항상 검증                |
| 끝없는 탐색      | 범위 없는 "조사해 줘"로 수백 개 파일을 읽음           | 조사 범위를 좁히거나 서브에이전트에 위임                |

## 정리

이 문서에서 다룬 방법은 "컨텍스트를 아껴 쓰고, Claude가 결과를 스스로 확인하게 한다"는 두 원칙을
실천하는 도구입니다. 주제별로 다시 묶으면 다음과 같습니다.

### 핵심 원칙

- 컨텍스트 창이 가장 중요한 자원입니다. 작업이 바뀌면 `/clear`하고, 많은 파일을 읽는 조사는
  서브에이전트에 맡깁니다.
- 테스트, 빌드, 스크린샷처럼 Claude가 직접 실행하고 읽을 수 있는 검증 수단을 함께 주고, "성공했다"는
  말 대신 실행한 명령과 출력 같은 근거를 요청합니다.
- 범위가 큰 작업은 plan mode로 탐색과 계획을 먼저 하고, 한 문장으로 설명할 수 있는 작은 작업은 바로
  요청합니다.
- 파일, 증상, 제약, 참고할 기존 패턴을 구체적으로 알려 줍니다. 요구 사항이 흐릿한 큰 기능은 인터뷰로 명세를
  먼저 만들고 새 세션에서 구현합니다.
- `CLAUDE.md`는 200줄 미만으로 짧게 유지하고, 가끔 필요한 지식은 스킬, 반드시 지킬 규칙은 훅으로
  분리합니다.
- 반복되는 승인 요청은 검토 없는 승인으로 이어지기 쉬우므로, 신뢰하는 명령은 `/permissions`나
  `/sandbox`로 미리 정리합니다.

### 상황별로 꺼내 쓸 방법

| 상황                                | 사용할 방법                                             |
| ----------------------------------- | ------------------------------------------------------- |
| 무엇이 컨텍스트를 차지하는지 궁금함 | `/context`                                              |
| 접근 방식이 불확실한 여러 파일 변경 | plan mode(`Shift+Tab`, `claude --permission-mode plan`) |
| 파일, 스크린샷, 로그를 함께 넘김    | `@경로`, `Ctrl+V`, 파이프로 `claude -p`에 전달          |
| 진행 방향이 틀렸음                  | `Esc`로 멈추고 바로 지시를 바꿈                         |
| 대화나 코드를 이전 상태로 되돌림    | `Esc` 두 번 또는 `/rewind`, Bash로 바꾼 내용은 git으로  |
| 같은 수정 요청이 두 번 넘게 실패함  | `/clear` 후 배운 점을 반영한 프롬프트로 재시작          |
| 긴 작업 중 컨텍스트가 부족함        | `/compact <지시>`                                       |
| 이전에 하던 작업을 이어 감          | `claude --continue`, `claude --resume`, `/rename`       |
| CI나 스크립트에서 실행함            | `claude -p`, `--output-format json`, `--allowedTools`   |
| 여러 작업을 동시에 진행함           | `claude --worktree <이름>`으로 세션마다 별도 worktree   |
| 외부 서비스와 연동함                | CLI 도구를 우선 쓰고, CLI가 없으면 MCP 서버 연결        |
| 매번 지켜야 하는 규칙을 자꾸 빠뜨림 | 훅으로 강제                                             |

### 작업을 시작하기 전 확인할 질문

- Claude가 작업의 성공 여부를 직접 확인할 방법을 주었나요?
- 변경 내용을 한 문장으로 설명할 수 있나요? 아니라면 계획부터 세웠나요?
- 현재 세션에 관련 없는 이전 작업의 컨텍스트가 남아 있지 않나요?
- 매번 반복해서 말하는 규칙이 있다면 `CLAUDE.md`나 훅으로 옮길 수 있나요?

위 방법은 출발점일 뿐입니다. 복잡한 문제 하나를 깊게 파고들 때는 컨텍스트를 유지하는 편이 나을 수도 있으니,
결과가 좋았을 때와 나빴을 때 무엇이 달랐는지 관찰하며 자신에게 맞는 방식을 찾아 갑니다.
