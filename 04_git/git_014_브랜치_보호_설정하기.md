# 브랜치 보호 설정하기

Git 작업할 때 특정 브랜치에 대해서 보호 또는 룰 설정이 필요할 때가 있습니다.

예를들면, main 브랜치에 force push 를 막아야 하는 경우입니다.

![git-protect-branch](./assets/git-protect-branch.png)

## 설정 방법

- 저장소 페이지에서 Settings → Rules → Rulesets로 이동합니다.
- New ruleset → New branch ruleset을 선택합니다.
- 이름을 입력합니다. 예: Protect main
- Enforcement status를 Active로 설정합니다.
- Target branches에서 Include by pattern을 선택하고 main을 입력합니다.
- Rules 영역에서 Block force pushes가 선택되어 있는지 확인합니다.
  이 규칙은 기본적으로 활성화되어 있으므로, 해제하지 않는 것이 핵심입니다.
- Bypass list를 확인합니다. 관리자나 특정 사용자·팀·GitHub App을 우회 대상으로 추가했다면 그 대상은
  force push할 수 있으므로, 완전히 막으려면 비워 둡니다.
- Create를 눌러 저장합니다.

## 검증

검증은 로컬에서 다음처럼 수행할 수 있습니다.

```shell
git push --force origin main
```

보호가 정상 적용됐다면 GitHub가 push를 거부합니다.

## 주의할 점

기존에 Settings → Branches의 Branch protection rule이 main에 적용되어 있는 경우입니다.
Ruleset과 함께 동작할 수 있으므로, 서로 상충되는 규칙이나 우회 권한이 없는지 함께 확인하는 것이 좋습니다.

관리자도 예외 없이 막으려면 Ruleset의 bypass 목록에 관리자를 넣지 않아야 합니다.

GitHub 공식 문서상 force push 차단 규칙은 대상 브랜치의 이력을 덮어써서 커밋이 사라지는 일을 방지합니다.

## Tips

Ruleset의 규칙은 Target branches에서 지정한 브랜치에 적용됩니다. GitHub 화면의
`matching refs`는 여기서는 `main`처럼 규칙과 이름이 일치하는 브랜치를 뜻합니다.
규칙을 많이 켠다고 항상 좋은 것은 아닙니다. 팀의 배포 방식과 CI 설정에 맞는 규칙만
선택해야 작업이 불필요하게 막히지 않습니다.

### Restrict creations

규칙과 일치하는 이름의 브랜치나 태그를 새로 만드는 작업을 막습니다. Bypass 권한을
받은 사용자만 만들 수 있습니다.

- `main` 브랜치가 이미 존재한다면 일반적인 보호 목적에는 보통 필요하지 않습니다.
- `release/*`처럼 정해진 이름의 배포 브랜치를 관리자만 만들게 하고 싶을 때 사용합니다.

### Restrict updates

규칙과 일치하는 브랜치에 `push`로 내용을 추가하거나 변경하는 작업을 막습니다.
Bypass 권한이 있는 사용자만 직접 업데이트할 수 있습니다.

- 모든 변경을 Pull Request로만 `main`에 반영하고 싶을 때 사용할 수 있습니다.
- 단, Pull Request 병합을 수행하는 사용자 또는 GitHub Actions가 Bypass 권한을
  필요로 할 수 있으므로, 현재 병합 방식과 자동화 계정을 먼저 확인해야 합니다.

### Restrict deletions

규칙과 일치하는 브랜치나 태그의 삭제를 막습니다. Bypass 권한이 있는 사용자만
삭제할 수 있습니다.

- `main`이 실수로 삭제되는 것을 막기 위해 보통 활성화합니다.
- 기본 브랜치는 원래 삭제가 제한되지만, 기본 브랜치를 바꾼 뒤의 실수도 대비할 수
  있습니다.

### Require linear history

병합 커밋(부모 커밋이 둘 이상인 커밋)이 대상 브랜치에 들어오는 것을 막습니다.
커밋 이력이 한 줄로 이어져 `git log`를 읽고 되돌리기 쉬워집니다.

- Pull Request 병합 방식은 `Squash merge` 또는 `Rebase merge`를 사용해야 합니다.
- 저장소 설정에서 이 병합 방식을 하나 이상 허용하지 않으면 설정할 수 없습니다.

### Require deployments to succeed

Pull Request 변경 사항이 지정한 배포 환경에 성공적으로 배포된 뒤에만 대상 브랜치에
반영하도록 요구합니다.

- 예를 들어 `staging` 환경의 배포와 점검이 성공한 코드만 `main`에 병합할 수 있게
  합니다.
- GitHub Environments와 배포 상태를 보고하는 CI/CD가 먼저 구성되어 있어야 합니다.
  단순히 서버에 배포하는 스크립트만으로는 충족되지 않을 수 있습니다.

### Require signed commits

대상 브랜치에 들어오는 커밋에 검증된 전자 서명을 요구합니다. 커밋 작성자가 설정한
GPG 키 또는 SSH 키로 서명했는지 GitHub가 확인합니다.

- 오픈 소스나 보안 요구가 높은 저장소에서 커밋 출처 확인에 유용합니다.
- 팀원과 CI 봇 모두 서명 설정이 필요하며, 기존의 서명되지 않은 커밋이 포함된
  Pull Request가 병합되지 않을 수 있습니다.

### Require a pull request before merging

대상 브랜치에 직접 커밋을 올리지 못하게 하고, 다른 브랜치에서 만든 변경을 Pull
Request 검토와 병합으로만 반영하게 합니다.

- `main` 보호에서 가장 많이 사용하는 규칙입니다.
- 최소 승인 수, 마지막 변경 후 재승인, 코드 소유자 승인 같은 세부 조건을 함께
  설정할 수 있습니다.
- 혼자 작업하는 저장소라면 Bypass 권한을 가진 사용자가 병합할 수 있는지 확인해야
  합니다.

### Require status checks to pass

지정한 CI 검사 결과가 성공해야 대상 브랜치를 업데이트할 수 있습니다. 예를 들어
테스트, 빌드, 린트 검사가 모두 통과해야 Pull Request를 병합할 수 있습니다.

- 먼저 GitHub Actions 등에서 해당 검사를 실행하고 성공 결과를 GitHub에 보고해야
  목록에서 선택할 수 있습니다.
- 같은 이름의 검사 job이 여러 워크플로에 있으면 어떤 결과를 요구하는지 모호해질 수
  있으므로 job 이름을 고유하게 정하는 편이 좋습니다.

### Block force pushes

`git push --force` 또는 이와 동등한 강제 push를 막습니다. 강제 push는 원격 브랜치
이력을 다른 커밋으로 바꾸므로, 다른 사람이 기준으로 삼은 커밋과 Pull Request가
사라지거나 꼬일 수 있습니다.

- `main`에는 기본적으로 활성화하는 것을 권장합니다.
- 예외 사용자가 필요하다면 Bypass 목록에 추가할 수 있지만, 이력이 바뀌는 작업은
  팀에 공유하고 백업 지점을 남긴 뒤 수행해야 합니다.

### Require code scanning results

지정한 코드 스캔 도구가 분석 결과를 보고하도록 요구하고, 설정한 수준의 보안 문제가
있으면 대상 브랜치 업데이트를 막습니다.

- CodeQL 같은 코드 분석 도구가 대상 커밋과 기준 브랜치 모두에 대해 결과를
  생성해야 합니다.
- 취약점 정책이 준비되지 않은 상태에서 바로 켜면 기존 경고 때문에 모든 병합이
  막힐 수 있으므로, 경고 정리 기준과 예외 처리 절차를 먼저 정합니다.

### Require code quality results

코드 품질 분석 결과가 지정한 심각도 이상이면 Pull Request 병합을 막습니다. 코드
복잡도, 중복, 유지보수성처럼 보안 외의 품질 기준을 자동으로 확인하는 데 사용합니다.

- GitHub에 결과를 제공하는 코드 품질 분석 도구와 Pull Request 분석이 필요합니다.
- 처음에는 높은 심각도만 차단하고, 팀의 기준이 자리 잡으면 범위를 넓히는 편이
  안전합니다.

### Restrict code coverage

Pull Request의 테스트 커버리지가 정한 최소 기준을 충족하지 못하면 병합을 막습니다.
커버리지는 테스트가 실행한 코드의 비율을 뜻합니다.

- 전체 라인 커버리지와 새로 바뀐 코드의 커버리지를 구분해 기준을 정할 수 있습니다.
- 커버리지는 테스트 품질 자체를 보장하지 않습니다. 숫자를 맞추기 위한 의미 없는
  테스트가 늘지 않도록 코드 리뷰와 함께 사용합니다.

### Automatically request Copilot code review

새 Pull Request가 열리면 작성자에게 Copilot code review 사용 권한과 남은 요청
한도가 있는 경우 Copilot에 자동 코드 리뷰를 요청합니다.

- 사람이 하는 승인과 코드 리뷰를 대체하지 않으며, 보조 검토 단계로 사용합니다.
- 이 기능을 사용하려면 작성자가 Copilot code review를 사용할 수 있어야 합니다.
