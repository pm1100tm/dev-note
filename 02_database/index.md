# 인덱스란 무엇이며 어떻게 설계하는가

인덱스는 테이블의 특정 컬럼 값을 별도 자료구조로 정리해 원하는 행을 빠르게 찾도록
돕습니다. 책의 색인처럼 전체 테이블을 매번 읽는 대신 후보 행의 위치를 좁힐 수 있습니다.

## 인덱스가 필요한 이유

인덱스가 없으면 조건에 맞는 행을 찾기 위해 테이블 전체를 읽는 순차 스캔이 발생할 수
있습니다. 데이터가 커질수록 읽어야 하는 블록과 응답 시간이 증가하고, 동시에 실행되는
요청이 많으면 저장장치와 CPU 부하가 커집니다.

다만 인덱스가 항상 빠른 것은 아닙니다. 결과 행이 테이블 대부분을 차지하거나 테이블이
작다면 순차 스캔이 더 저렴할 수 있으며, 최종 선택은 옵티마이저가 통계와 비용을 바탕으로
결정합니다.

## 대표적인 인덱스

- **B-tree**: 기본 인덱스입니다. 등가 비교, 범위 검색, 정렬에 적합합니다.
- **Hash**: 등가 비교 중심의 인덱스입니다. 범위 검색에는 사용할 수 없습니다.
- **GIN**: 배열, `jsonb`, 전문 검색처럼 하나의 행에서 여러 키를 검색할 때 유용합니다.
- **GiST**: 공간 데이터나 범위 타입처럼 다양한 연산자를 지원하는 구조입니다.
- **BRIN**: 물리적 저장 순서와 값의 상관관계가 높은 대용량 테이블에 적합합니다.

## 단일 인덱스와 복합 인덱스

```sql
CREATE INDEX idx_emp_deptno ON emp (deptno);
CREATE INDEX idx_emp_deptno_hiredate ON emp (deptno, hiredate);
```

복합 인덱스는 일반적으로 왼쪽 컬럼부터 조건에 사용됩니다. 따라서
`(deptno, hiredate)` 인덱스는 `deptno` 조건에는 유리하지만 `hiredate`만 조건으로
사용하는 쿼리에는 기대한 효과가 없을 수 있습니다. 실제 쿼리의 선택도와 정렬·조인
패턴을 기준으로 컬럼 순서를 정해야 합니다.

## 인덱스 설계 체크리스트

- WHERE, JOIN, ORDER BY에서 반복적으로 사용되는 컬럼인가?
- 값의 종류가 충분히 다양해 후보 행을 크게 줄일 수 있는가?
- 컬럼에 함수를 적용하거나 앞에 와일드카드를 사용해 인덱스를 무효화하고 있지 않은가?
- 쓰기 빈도와 인덱스 유지 비용을 감당할 수 있는가?
- 중복되거나 사용되지 않는 인덱스가 이미 존재하지 않는가?
- 부분 인덱스·표현식 인덱스·커버링 인덱스가 더 적합한가?

예를 들어 다음과 같이 조건이 고정된 조회가 많다면 부분 인덱스를 고려할 수 있습니다.

```sql
CREATE INDEX idx_orders_open_created_at
ON orders (created_at)
WHERE status = 'OPEN';
```

## 실행 계획으로 검증하기

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT *
FROM emp
WHERE deptno = 10;
```

`EXPLAIN`은 계획을 실행하지 않고 비용을 추정합니다. `EXPLAIN ANALYZE`는 실제로
쿼리를 실행해 예측 행 수와 실제 행 수, 실행 시간을 보여주므로 DML에서는 데이터가
변경될 수 있다는 점을 반드시 고려해야 합니다.

인덱스 추가 전후에는 동일한 데이터와 조건에서 계획, 실제 시간, 읽은 블록 수,
쓰기 작업 증가를 함께 비교해야 합니다. 인덱스를 추가하는 것만으로 성능 개선을
가정하지 말고 대표 트래픽으로 검증합니다.
