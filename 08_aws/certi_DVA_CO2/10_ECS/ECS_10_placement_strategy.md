# ECS Task Placement Strategy(배치 전략)

> 확인일: 2026-09-30

ECS에서 EC2 Launch Type을 사용할 때는 하나의 클러스터에 여러 EC2 컨테이너 인스턴스가 있습니다.

새 태스크를 시작하거나 서비스의 태스크 수를 줄일 때, ECS는 어느 인스턴스에 태스크를 둘지 결정해야 합니다.

`Task Placement Strategy`는 이 선택의 우선순위를 정하는 배치 알고리즘입니다.
비용, 고가용성, 인스턴스 간 작업 분산이라는 운영 목표에 맞춰 선택합니다.

공식 문서: [Amazon ECS task placement strategies](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-placement-strategies.html)

## 적용 범위와 기본 개념

- 이 기능은 **EC2 Launch Type의 ECS 태스크만** 지원합니다.
- Fargate는 실행 서버를 AWS가 관리하므로 사용자가 배치 전략이나 배치 제약 조건을 지정할 수 없습니다.
- Fargate는 접근 가능한 가용 영역에 태스크를 가능한 한 고르게 분산하려고 시도합니다.

ECS 서비스에서 별도로 전략을 지정하지 않으면 기본값은

- `spread`
- `attribute:ecs.availability-zone`
- 의 조합입니다.

즉, 같은 서비스의 태스크를 가용 영역에 고르게 나누려 합니다.

> 반면 `RunTask`로 직접 실행하는 독립 태스크는 이 서비스 기본 전략의 대상이 아닙니다.

배치 전략은 **최선 노력(best effort)** 입니다. 가장 이상적인 인스턴스에
여유 자원이 없으면 ECS는 실행 가능한 다른 인스턴스를 선택할 수 있습니다.
따라서 전략만으로 반드시 한 인스턴스에 하나의 태스크를 보장할 수는 없습니다.

## ECS가 태스크를 배치하는 순서

전략은 처음부터 모든 EC2 인스턴스를 대상으로 적용되지 않습니다.
ECS는 다음 순서로 후보를 줄인 뒤 전략을 적용합니다.

- 태스크 정의의 CPU, GPU, 메모리와 포트 요구 사항을 만족하는 인스턴스를 찾습니다.
- Task Placement Constraint를 만족하는 인스턴스만 남깁니다.
- Task Placement Strategy에 따라 남은 인스턴스의 우선순위를 정합니다.
- 최종 인스턴스를 선택해 태스크를 배치합니다.

예를 들어 메모리 `512 MiB`가 필요한 태스크라도, 남은 메모리가
`256 MiB`인 인스턴스에는 배치할 수 없습니다.

`binpack` 전략은 이처럼 실행 가능한 후보 안에서만 동작합니다.

## 배치 전략 세 가지

| 전략      | 동작                                                            | 적합한 상황                                         |
| --------- | --------------------------------------------------------------- | --------------------------------------------------- |
| `binpack` | 사용 후 남는 CPU 또는 메모리가 가장 적은 인스턴스를 우선합니다. | EC2 수와 유휴 용량을 줄이고 싶을 때                 |
| `random`  | 후보 인스턴스 중 하나를 무작위로 고릅니다.                      | 특별한 분산 또는 밀집 요구가 없을 때                |
| `spread`  | 지정한 값의 그룹별 태스크 수가 고르게 되도록 배치합니다.        | 가용 영역이나 인스턴스에 분산해 장애 영향을 줄일 때 |

### binpack: 빈 공간을 적게 남기기

- `binpack`은 `cpu` 또는 `memory`를 기준으로 설정합니다.
- 태스크를 넣은 뒤 사용 가능 자원이 가장 적게 남는 EC2 인스턴스를 선택합니다.
- 그 결과 태스크가 소수의 인스턴스에 밀집되고, 사용하지 않는 EC2 인스턴스를 줄여
  비용을 절감하기 좋습니다.

다만 태스크가 한 인스턴스에 많이 모일 수 있습니다.
해당 인스턴스에 장애가 발생하면 동시에 영향을 받는 태스크도 늘어납니다.
웹 서비스처럼 가용 영역 분산이 중요한 경우에는 `spread`와 함께 사용합니다.

서비스를 축소할 때 `binpack`을 사용하면, 태스크를 중지한 뒤 가장 많은
자원이 남게 되는 인스턴스의 태스크를 ECS가 우선 종료합니다. 비어 있는
인스턴스를 만들기 쉬워 Auto Scaling Group의 축소와도 잘 맞습니다.

### random: 무작위로 선택하기

- `random`은 별도의 기준 필드 없이 실행 가능한 후보 중 하나를 무작위로 선택합니다.
- 단순하지만 균등한 분산이나 비용 최적화를 보장하지 않습니다.

특별한 배치 목표가 없다면 사용할 수 있지만, 운영 요구 사항이 있다면
의도를 명확히 드러내는 `spread` 또는 `binpack`을 선택하는 편이 좋습니다.

### spread: 특정 기준으로 고르게 나누기

`spread`는 지정한 필드의 값마다 태스크 수가 비슷해지도록 배치합니다.

대표적인 필드는 다음과 같습니다.

- `attribute:ecs.availability-zone`: 가용 영역별로 태스크를 분산합니다.
- `instanceId` 또는 `host`: EC2 컨테이너 인스턴스별로 태스크를 분산합니다.
- `attribute:이름`: ECS 기본 속성 또는 직접 추가한 사용자 지정 속성으로
  분산합니다.

예를 들어 두 가용 영역에 EC2 인스턴스가 있고 태스크를 4개 실행하면,
`attribute:ecs.availability-zone` 기준 `spread`는 각 가용 영역에 2개씩
배치하려고 합니다.

서비스 축소 시에는 가용 영역 간 균형을 유지하도록 종료 대상을 고르며, 같은 가용 영역 안에서는 무작위로 선택합니다.

## 전략 조합과 적용 순서

여러 전략을 배열로 지정할 수 있으며, **작성한 순서대로** 적용합니다.

일반적인 조합은 먼저 가용 영역에 분산하고, 각 가용 영역 안에서는
메모리 기준으로 밀집 배치하는 방식입니다.

```json
"placementStrategy": [
  {
    "type": "spread",
    "field": "attribute:ecs.availability-zone"
  },
  {
    "type": "binpack",
    "field": "memory"
  }
]
```

이 설정은 먼저 가용 영역 간 균형을 고려하고, 같은 가용 영역의 후보 중에는
남은 메모리가 적은 인스턴스를 우선합니다.

> 순서를 반대로 하면 비용 밀집을 먼저 고려하므로 가용 영역 분산 결과가 달라질 수 있습니다.

- 배치 전략은 서비스 생성·갱신 또는 `RunTask` 호출에서 지정할 수 있습니다.
- 변경한 전략은 기존에 실행 중인 태스크를 자동으로 옮기지 않습니다.
- 새로 배치되는 태스크부터 영향을 받는다는 점을 배포 계획에 반영해야 합니다.

## 배치 제약 조건과의 차이

Task Placement Constraint는 태스크를 둘 수 있는 EC2 인스턴스를 **제한하는 필수 규칙**입니다.

전략이 "어느 후보를 더 선호할지"를 정한다면, 제약 조건은 "어떤 후보를 허용할지"를 정합니다.

| 제약 조건          | 의미                                                            | 예시                                                |
| ------------------ | --------------------------------------------------------------- | --------------------------------------------------- |
| `distinctInstance` | 활성 태스크를 서로 다른 EC2 인스턴스에 배치합니다.              | 동일 서비스 복제본을 호스트 장애에서 분리합니다.    |
| `memberOf`         | Cluster Query Language 표현식을 만족하는 인스턴스만 허용합니다. | GPU 인스턴스 또는 `stack=prod` 속성에만 배치합니다. |

`memberOf`는 ECS 기본 속성 또는 사용자 지정 속성을 사용합니다.
예를 들어, `attribute:ecs.instance-type == g2.2xlarge`는 해당 인스턴스
유형만 후보로 남깁니다.

`attribute:ecs.availability-zone` 같은 기본 속성과 `stack=prod` 같은
사용자 지정 속성을 조합할 수도 있습니다.

제약 조건을 만족하는 인스턴스가 하나도 없으면 ECS는 태스크를 실행하지
못하고 `PENDING` 상태로 유지합니다.

따라서 `distinctInstance`를 사용할 때는 원하는 태스크 수만큼 서로 다른 EC2 인스턴스가 있는지 먼저
확인해야 합니다.

`distinctInstance`는 배치 시점의 활성 태스크를 기준으로 판단합니다.

강한 실행 환경 격리가 필요하다면 태스크마다 하드웨어 가상화 환경을 쓰는
Fargate를 별도로 검토합니다.

공식 문서: [Amazon ECS task placement constraints](https://docs.aws.amazon.com/AmazonECS/latest/developerguide/task-placement-constraints.html)

## 선택 가이드

| 목표                                  | 권장 설정                                    | 주의할 점                                         |
| ------------------------------------- | -------------------------------------------- | ------------------------------------------------- |
| EC2 비용과 유휴 용량을 줄입니다.      | `binpack` + `memory` 또는 `cpu`              | 호스트 장애의 영향 범위가 커질 수 있습니다.       |
| 가용 영역 장애에 대비합니다.          | `spread` + `attribute:ecs.availability-zone` | 각 가용 영역에 충분한 EC2 용량이 필요합니다.      |
| 동일 호스트에 복제본을 두지 않습니다. | `distinctInstance` + 필요 시 `spread`        | 복제본 수만큼 EC2 인스턴스가 필요합니다.          |
| 특정 인스턴스 유형에서만 실행합니다.  | `memberOf` + 필요한 전략                     | 조건에 맞는 인스턴스가 없으면 `PENDING`이 됩니다. |

핵심은 제약 조건으로 실행 가능한 후보를 안전하게 한정한 뒤, 전략으로
비용과 가용성의 우선순위를 정하는 것입니다. 또한 태스크 수만 늘려서는
부족할 수 있으므로, EC2 클러스터의 CPU·메모리·포트 용량과 Auto Scaling
Group의 확장 정책도 함께 설계해야 합니다.
