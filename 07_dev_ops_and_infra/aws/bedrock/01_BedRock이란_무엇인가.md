# Bedrock 이란 무엇인가

## 한 문장으로 이해하기

**Amazon Bedrock은 여러 회사의 생성형 AI 모델을 AWS 안에서 API로 사용할 수 있게 해 주는 완전 관리형 서비스다.**

쉽게 비유하면 Bedrock은 다음 두 가지를 합친 서비스다.

- 여러 AI 모델을 고를 수 있는 **모델 마켓**
- 선택한 모델을 서버 구축 없이 호출하게 해 주는 **관리형 실행 환경**

개발자는 GPU 서버를 직접 준비하거나 모델 배포 환경을 운영하는 대신, 필요한 모델을 선택하고 AWS SDK 또는 API로 호출하면 된다.
AWS 공식 문서에서는 Bedrock을 주요 AI 회사의 파운데이션 모델에 안전하게 접근할 수 있는 완전 관리형 서비스로 설명한다.

> Bedrock 자체가 하나의 AI 모델은 아니다. 여러 파운데이션 모델을 사용하고, 생성형 AI 애플리케이션에 필요한 기능을
> 조합할 수 있게 해 주는 AWS 서비스다.

## 먼저 알아둘 용어

### 생성형 AI

사용자의 요청을 입력받아 텍스트, 이미지, 코드, 음성 같은 새로운 결과를 만드는 AI다.

예를 들면 다음과 같은 작업을 할 수 있다.

- 질문에 답하는 챗봇
- 긴 문서 요약
- 이메일 또는 상품 설명 생성
- 번역과 문장 교정
- 이미지 생성
- 문서를 검색해 답변하는 사내 지식 검색

### 파운데이션 모델

파운데이션 모델(Foundation Model, FM)은 대규모 데이터로 미리 학습되어 여러 작업에 활용할 수 있는 범용 AI 모델이다.
대규모 언어 모델(LLM)은 주로 언어를 다루는 파운데이션 모델의 한 종류다.

Bedrock에서는 Amazon과 여러 외부 모델 제공자의 모델을 선택할 수 있다. 모델마다 지원하는 입력 형식, 최대 입력 길이,
품질, 속도, 가격, 사용 가능한 리전과 API가 다르므로 이름만 보고 선택하면 안 된다.

### 프롬프트와 토큰

- **프롬프트**: 모델에 전달하는 질문, 지시문, 문맥
- **토큰**: 모델이 텍스트를 처리하고 비용을 계산할 때 사용하는 작은 단위
- **추론(Inference)**: 학습된 모델에 입력을 보내 결과를 생성하는 과정

입력과 출력이 길어질수록 일반적으로 처리 시간과 토큰 비용이 증가한다.

## 기본 동작 흐름

가장 단순한 챗봇은 다음 순서로 동작한다.

```text
사용자
  ↓ 질문
웹 또는 모바일 애플리케이션
  ↓ HTTPS
백엔드 서버(Lambda, ECS, EC2 등)
  ↓ AWS SDK + IAM 권한
Amazon Bedrock Runtime
  ↓ 모델 실행
파운데이션 모델
  ↓ 생성 결과
백엔드 서버
  ↓ 검증·가공
사용자
```

중요한 점은 프론트엔드에서 Bedrock을 직접 호출하지 않는 것이다. 브라우저나 앱에 AWS 자격 증명을 넣으면 유출 위험이 있고,
사용량 제한·입력 검증·응답 필터링·비용 통제를 일관되게 적용하기 어렵다. 일반적으로 인증된 백엔드가 Bedrock을 호출해야 한다.

## Bedrock이 대신 관리하는 것

- 파운데이션 모델을 실행할 인프라
- 모델 추론용 관리형 API
- AWS IAM을 이용한 접근 제어
- CloudWatch, CloudTrail 등 AWS 서비스와의 연동
- 필요에 따른 온디맨드 또는 프로비저닝된 처리량
- Knowledge Bases, Guardrails, 평가, 모델 사용자 지정 같은 생성형 AI 구축 기능

반면 다음 항목은 애플리케이션 개발자가 책임져야 한다.

- 어떤 모델이 요구사항에 적합한지 평가
- 프롬프트와 대화 문맥 설계
- 사용자의 인증·인가
- 개인정보와 기밀정보의 입력 통제
- 잘못된 답변에 대한 검증과 업무 규칙 적용
- 재시도, 타임아웃, 사용량 제한, 모니터링
- 비용 한도와 장애 대응

> 관리형 서비스라고 해서 AI 답변의 정확성까지 AWS가 보장하는 것은 아니다. 생성형 AI는 사실과 다른 내용을 그럴듯하게
> 답하는 환각(Hallucination)을 일으킬 수 있다.

## 주요 기능

### 1. 여러 파운데이션 모델 사용

하나의 AWS 환경에서 다양한 모델을 비교하고 사용할 수 있다. 텍스트 생성뿐 아니라 모델에 따라 이미지, 음성, 비디오, 임베딩 등도 처리할 수 있다.

지원 모델과 기능은 계속 변경되며 리전별 차이도 있다. 구현 전에
[지원 모델 목록](https://docs.aws.amazon.com/bedrock/latest/userguide/models-supported.html)과
[API 호환성 표](https://docs.aws.amazon.com/bedrock/latest/userguide/models-api-compatibility.html)를
확인해야 한다.

### 2. 모델 추론 API

Bedrock에는 용도별 API가 있다.

- **Converse / ConverseStream**: 여러 지원 모델에 공통된 형식으로 대화형 요청을 보낼 때 적합하다.
- **InvokeModel / InvokeModelWithResponseStream**: 모델별 고유 요청 형식이나 세부 기능을 직접 사용할 때 적합하다.
- **OpenAI 호환 API와 Messages API**: 지원되는 모델과 엔드포인트에 한해 기존 SDK 방식과 유사하게 연동할 수 있다.

처음 대화형 애플리케이션을 만든다면 모델 교체가 비교적 쉬운 `Converse` API부터 검토하는 편이 실용적이다.
단, 모든 모델이 모든 API를 지원하지는 않는다.

### 3. Knowledge Bases와 RAG

파운데이션 모델은 회사 내부 규정이나 최신 사내 문서를 기본적으로 알지 못한다. RAG(Retrieval-Augmented Generation)는
질문과 관련된 문서를 먼저 검색하고, 검색 결과를 프롬프트에 함께 넣어 답변하게 하는 방식이다.

```text
사용자 질문
  ↓
관련 사내 문서 검색
  ↓
질문 + 검색된 문서 조각
  ↓
모델 답변 + 출처
```

Bedrock Knowledge Bases는 데이터 수집, 임베딩, 벡터 검색, 검색 결과를 이용한 답변 생성을 관리형 기능으로 제공한다.
RAG는 모델을 다시 학습시키는 기술이 아니며, 검색 품질과 원본 문서 품질이 낮으면 답변도 좋아지기 어렵다.

### 4. Guardrails

Guardrails는 사용자 입력과 모델 출력을 검사해 애플리케이션의 안전 정책을 적용한다. 유해 콘텐츠, 금지 주제, 특정 단어,
민감정보 등을 필터링할 수 있다.

Guardrails는 중요한 방어 계층이지만 완벽한 보안 장치는 아니다. 권한 검사, 업무 규칙, 출력 검증, 사람의 승인 절차가
필요한 업무를 Guardrails 하나로 대체하면 안 된다.

### 5. 모델 평가와 사용자 지정

모델별 응답 품질을 평가하고, 지원되는 모델은 파인튜닝 같은 방식으로 특정 용도에 맞게 사용자 지정할 수 있다.
대부분의 프로젝트는 먼저 기본 모델과 좋은 프롬프트, RAG로 요구사항을 검증한 뒤 사용자 지정을 고려하는 편이 비용과 운영
복잡도를 줄인다.

## Bedrock의 두 API 영역

처음 사용할 때 `bedrock` 클라이언트와 `bedrock-runtime` 클라이언트를 혼동하기 쉽다.

| 영역              | 주된 역할               | 예시                                         |
| ----------------- | ----------------------- | -------------------------------------------- |
| `bedrock`         | 모델과 리소스 조회·관리 | 사용 가능한 모델 조회, 사용자 지정 작업 관리 |
| `bedrock-runtime` | 실제 추론 실행          | 프롬프트 전송, 응답 또는 스트림 수신         |

즉, **모델 정보를 관리하는 API**와 **모델에게 실제 질문하는 API**가 분리되어 있다고 이해하면 된다.

## 모델을 선택하는 기준

유명하거나 가장 큰 모델이 항상 정답은 아니다. 최소한 다음 항목을 같은 테스트 데이터로 비교해야 한다.

- 1. **품질**: 실제 업무 질문에 정확히 답하는가?
- 2. **비용**: 입력·출력 토큰과 부가 기능 비용이 예산에 맞는가?
- 3. **지연 시간**: 사용자가 기다릴 수 있는 시간 안에 응답하는가?
- 4. **기능**: 스트리밍, 도구 사용, 이미지 입력, 구조화 출력 등을 지원하는가?
- 5. **리전**: 서비스할 리전에서 모델과 필요한 기능을 지원하는가?
- 6. **쿼터**: 예상 트래픽을 처리할 수 있는가?
- 7. **수명 주기**: 모델 버전 변경이나 지원 종료에 대응할 수 있는가?

모델 ID를 소스 코드 여러 곳에 하드코딩하지 말고 환경별 설정으로 분리하는 것이 안전하다. 모델을 교체하면 품질과 출력 형식이
달라질 수 있으므로 회귀 평가도 필요하다.

## 비용은 어떻게 발생하는가

일반적인 온디맨드 텍스트 모델은 입력 토큰과 출력 토큰 사용량을 기준으로 과금한다. 모델, 리전, 처리 방식에 따라 가격이
다르며 Knowledge Bases, Guardrails, 모델 평가, 사용자 지정 모델 등은 별도 비용이 발생할 수 있다. 일정 처리량을
확보하는 Provisioned Throughput은 시간 단위 비용과 약정 조건을 확인해야 한다.

초보자가 자주 놓치는 비용 요인은 다음과 같다.

- 대화 기록 전체를 매 요청마다 보내면서 증가하는 입력 토큰
- 필요 이상으로 크게 설정한 최대 출력 토큰
- 실패 요청에 대한 무제한 재시도
- RAG에서 사용하는 임베딩 모델과 벡터 저장소
- 요청·응답 로깅에 사용하는 CloudWatch Logs와 S3
- 삭제하지 않은 Provisioned Throughput 또는 관련 리소스

정확한 금액은 바뀔 수 있으므로 구현 시점에 [Amazon Bedrock 요금](https://aws.amazon.com/bedrock/pricing/)을 확인한다.

## 보안과 개인정보

AWS 문서에 따르면 모델 제공자는 Bedrock의 로그와 고객 프롬프트·완성 결과에 접근할 수 없다. 하지만 이것이 아무 데이터나
프롬프트에 넣어도 된다는 뜻은 아니다.

운영 환경에서는 다음 원칙을 적용한다.

- IAM 최소 권한으로 호출 가능한 모델과 작업을 제한한다.
- 프론트엔드에 장기 AWS 액세스 키를 저장하지 않는다.
- 개인정보, 인증정보, 영업비밀은 전송 전에 마스킹하거나 정책에 따라 차단한다.
- 프롬프트와 응답을 로그에 남길 때 민감정보를 제거하고 보존 기간을 정한다.
- 필요한 경우 KMS 암호화, VPC 엔드포인트, CloudTrail 감사 로그를 검토한다.
- 모델의 답변을 SQL, 셸 명령, 송금·결제 같은 고위험 작업에 바로 실행하지 않는다.
- 외부 모델의 사용 조건과 AWS Marketplace 구독 조건을 확인한다.

자세한 기준은 [Amazon Bedrock 데이터 보호](https://docs.aws.amazon.com/bedrock/latest/userguide/data-protection.html)와
[IAM 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/security-iam.html)를 참고한다.

## 처음 시작할 때의 순서

- 1. 사용할 AWS 리전에서 Bedrock과 대상 모델을 지원하는지 확인한다.
- 2. 실습용 IAM 역할에 필요한 최소 권한을 부여한다.
- 3. 콘솔의 Playground에서 프롬프트와 모델 응답을 시험한다.
- 4. 작은 온디맨드 모델로 최소 API 호출을 구현한다.
- 5. 타임아웃, 오류 변환, 제한된 재시도와 지수 백오프를 추가한다.
- 6. 실제 업무 질문 세트로 품질·지연 시간·비용을 비교한다.
- 7. 민감정보 처리, 로깅, Guardrails와 사용자별 사용량 제한을 적용한다.
- 8. CloudWatch 지표와 비용 알림을 구성한 뒤 운영 트래픽을 점진적으로 늘린다.

일부 외부 모델은 최초 사용 시 AWS Marketplace 관련 권한이나 이용 조건 동의가 필요할 수 있다. 모델 접근 방식은 변경될
수 있으므로 [모델 접근 공식 문서](https://docs.aws.amazon.com/bedrock/latest/userguide/model-access.html)를
기준으로 설정한다.

## Bedrock과 SageMaker AI의 차이

| 구분        | Amazon Bedrock                                     | Amazon SageMaker AI                                      |
| ----------- | -------------------------------------------------- | -------------------------------------------------------- |
| 중심 목적   | 관리형 파운데이션 모델을 이용한 생성형 AI 앱 개발  | ML 모델의 데이터 준비, 학습, 배포와 MLOps 전반           |
| 인프라 관리 | 모델 추론 인프라를 대부분 서비스가 관리            | 인스턴스와 엔드포인트 구성을 더 세밀하게 제어            |
| 적합한 경우 | 빠르게 생성형 AI 기능을 만들고 여러 FM을 비교할 때 | 자체 ML 학습 파이프라인이나 세밀한 배포 제어가 필요할 때 |

둘은 경쟁 서비스라기보다 문제에 따라 함께 사용할 수도 있는 도구다. 생성형 AI API가 필요하다는 이유만으로 처음부터 직접 모델 서버를 운영하는 것은 대개 불필요한 복잡성을 만든다.

## 핵심 정리

- Bedrock은 모델이 아니라 **여러 생성형 AI 모델과 구축 기능을 제공하는 AWS 완전 관리형 서비스**다.
- 가장 단순한 사용법은 백엔드에서 `bedrock-runtime`의 추론 API를 호출하는 것이다.
- RAG는 내부 문서를 근거로 답하게 하고, Guardrails는 입력과 출력을 정책에 따라 검사한다.
- 모델의 품질·가격·기능·리전 지원은 서로 다르므로 실제 데이터로 평가해야 한다.
- 운영 환경에서는 IAM 최소 권한, 민감정보 보호, 비용 통제, 오류 처리와 결과 검증이 필수다.
