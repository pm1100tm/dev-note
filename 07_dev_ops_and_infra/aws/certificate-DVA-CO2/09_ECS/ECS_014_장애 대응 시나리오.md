# 장애 대응 시나리오

[전체 목차](<./ECS_001_컨테이너와 ECS 기본 개념.md>)

## 학습 목표

- 증상을 시작 전, 실행 중, 트래픽, 용량 문제로 분류한다.
- 오류 메시지에서 IAM, 네트워크, 리소스 원인을 구분한다.
- 시험 선택지에서 가장 직접적인 해결책을 찾는다.

## 기본 진단 순서

```text
최근 변경 확인
  -> ECS Service Events
  -> Task stopped reason / container exitCode
  -> CloudWatch Logs
  -> ALB Target Health
  -> IAM / Network / Capacity 세부 확인
```

처음부터 모든 설정을 바꾸지 않는다. 실제 오류 문구와 실패 단계에 따라 범위를 좁힌다.

## 시나리오 1: CannotPullContainerError

가능한 원인:

- Task Execution Role의 ECR 권한 부족
- Repository URI 또는 태그 오류
- 이미지 삭제
- private subnet의 NAT/VPC Endpoint/DNS 경로 부족
- 교차 계정 Repository Policy 오류

`AccessDenied`면 IAM과 Repository Policy를, `timeout`이면 네트워크와 DNS를 먼저 확인한다.

## 시나리오 2: ResourceInitializationError

Task 시작 준비 중 로그, secret, 인증 정보 또는 네트워크 초기화가 실패할 때 나타날 수 있다.

- secret ARN과 리전 확인
- Execution Role의 `secretsmanager:GetSecretValue` 또는 `ssm:GetParameters` 확인
- 고객 관리형 KMS 키 사용 시 `kms:Decrypt`와 Key policy 확인
- Secrets Manager/SSM/CloudWatch Logs로 가는 네트워크 경로 확인

## 시나리오 3: Task가 계속 교체됨

Task가 잠시 `RUNNING`이지만 Service가 반복 교체한다면 다음을 본다.

- ALB health check path, port, success code
- ALB SG에서 Task SG로 접근 가능 여부
- health check grace period
- 애플리케이션이 `0.0.0.0`과 올바른 port에서 listen하는지
- essential container 종료와 exit code

## 시나리오 4: OOM과 CPU 과부하

Exit code `137`은 SIGKILL 결과이며 메모리 제한 초과를 포함한 여러 원인을 조사해야 한다. CloudWatch 메모리 지표, 애플리케이션 로그, Task 중지 이유로 OOM 여부를 확인한다.

해결은 메모리 누수 수정, JVM/런타임 제한 조정, Task 크기 변경, 부하 분산을 함께 검토한다. 크기만 무작정 늘리면 원인을 가릴 수 있다.

## 시나리오 5: Task가 PENDING

EC2 Launch Type:

- 인스턴스 CPU/메모리 부족
- 필요한 host port 충돌
- 배치 constraint를 만족하는 인스턴스 없음
- ENI/IP 용량 부족
- 컨테이너 인스턴스 Agent 문제

Fargate:

- subnet의 가용 IP 부족
- 지원되지 않는 CPU/메모리 조합 또는 플랫폼 설정
- 리전/AZ 용량 및 quota 문제

## 시나리오 6: 애플리케이션 AWS API AccessDenied

Task는 정상 실행되고 로그도 전송되지만 앱의 S3/DynamoDB 호출만 실패한다면 Task Role을 확인한다. Execution Role에 앱 권한을 추가하는 것은 올바른 해결이 아니다.

교차 계정, KMS 암호화, S3 bucket policy처럼 identity policy 외의 정책도 함께 평가한다.

## 시나리오 7: 배포가 안정 상태에 도달하지 못함

- 새 revision의 이미지와 환경 변수 비교
- 새 Task의 로그와 health 상태 확인
- `minimumHealthyPercent`와 `maximumPercent`가 용량과 맞는지 확인
- Circuit Breaker와 rollback 상태 확인
- dependency와 DB migration 호환성 확인

## 실무 Runbook 형식

각 장애 문서에는 다음을 포함한다.

- 사용자 증상과 영향 범위
- 확인할 Dashboard와 명령
- 정상/비정상 판단 기준
- 즉시 완화와 근본 해결 분리
- rollback 조건
- 담당자와 escalation 경로

## 시험 포인트

| 증상 | 우선 확인 |
| --- | --- |
| ECR pull `AccessDenied` | Task Execution Role |
| 앱의 S3 `AccessDenied` | Task Role |
| ECR pull timeout | NAT/Endpoint/DNS/SG |
| ALB unhealthy | path, port, SG, grace period |
| EC2 Task `PENDING` | Cluster capacity와 placement |
| secret 주입 실패 | Execution Role, KMS, network |

## 연습문제

**문제.** 새 배포의 Task는 시작되지만 ALB에서 unhealthy가 되고 반복 종료된다. 컨테이너 로그에는 앱이 8080에서 정상 시작했다고 나온다. 첫 확인 항목은?

**정답:** Target Group health check port/path, Task Definition의 container port, Task SG가 ALB SG에서 8080을 허용하는지 확인한다.

## 확인 문제

- [ ] `AccessDenied`의 주체로 Role을 구분할 수 있다.
- [ ] `PENDING` 원인을 Launch Type별로 설명할 수 있다.
- [ ] 배포 장애의 즉시 완화와 근본 해결을 구분할 수 있다.
