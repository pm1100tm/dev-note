# 비용과 운영 최적화

[전체 목차](<./ECS_001_컨테이너와 ECS 기본 개념.md>)

## 학습 목표

- 컴퓨팅, 네트워크, 로그, 이미지 저장 비용을 함께 본다.
- Fargate 크기와 Scaling 정책을 데이터로 조정한다.
- 비용 절감이 안정성을 훼손하지 않도록 판단한다.

## 비용 구성 요소

ECS 자체의 제어 영역만 볼 것이 아니라 실제 사용 리소스를 확인한다.

- Fargate Task의 vCPU, 메모리, 실행 시간 및 추가 리소스
- EC2 인스턴스, EBS와 유휴 Cluster capacity
- ALB/NLB 사용량
- NAT Gateway 처리량과 시간
- CloudWatch Logs 수집, 저장, 쿼리
- ECR 이미지 저장과 데이터 전송
- Container Insights 등 상세 모니터링

## Right Sizing

너무 큰 Task는 지속적인 낭비를 만들고 너무 작은 Task는 OOM, throttling, 잦은 확장을 유발한다.

1. CPU/메모리의 평균뿐 아니라 peak와 percentile을 관찰한다.
2. GC, OOM, 응답 지연과 함께 분석한다.
3. Task 크기를 한 단계씩 조정하고 부하 테스트한다.
4. min/max Task 수와 배포 중 추가 용량까지 계산한다.

평균 CPU만 낮다고 바로 줄이지 않는다. 메모리 peak와 시작 시 리소스, 단일 Task 장애 시 남은 처리량도 본다.

## Fargate와 EC2 비용 판단

Fargate는 운영 인력과 유휴 용량을 줄이는 장점이 있다. EC2는 지속적인 고사용률과 예측 가능한 워크로드에서 구매 옵션과 bin packing으로 절감 여지가 있을 수 있지만 패치, 용량, Agent 운영 비용이 따른다.

가격만 단순 비교하지 말고 다음을 함께 본다.

- 팀의 운영 비용
- 사용률과 트래픽 변동
- 장애 및 패치 요구
- 특수 인스턴스 필요 여부
- 배포 시 여유 용량

## Spot 사용

중단을 허용할 수 있는 worker, batch, 재시도 가능한 Task는 Fargate Spot 또는 EC2 Spot을 검토한다. 안정적인 최소 용량은 온디맨드에 두고 추가 용량을 Spot으로 분산할 수 있다.

적합 조건:

- 상태가 S3, DB, SQS 등 외부에 저장됨
- 중복 실행에 안전하거나 idempotent함
- 종료 신호를 처리하고 재시도 가능함
- 특정 Task 중단이 전체 서비스 장애로 이어지지 않음

## Scaling 최적화

- 최소 Task 수는 가용성과 초기 응답 요구에 맞춘다.
- 최대 Task 수로 downstream DB와 비용을 보호한다.
- queue worker에는 CPU보다 backlog 지표를 검토한다.
- 예측 가능한 peak는 Scheduled Scaling으로 미리 준비한다.
- 과도한 scale-in/out 반복은 cooldown과 지표를 조정한다.

## 네트워크 비용

private subnet의 모든 외부 호출을 NAT Gateway로 보내면 처리 비용이 커질 수 있다. ECR, S3, CloudWatch Logs 등 통신 패턴과 데이터량을 분석해 VPC Endpoint의 시간/처리 비용과 비교한다.

같은 리전이라도 AZ 간 데이터 전송이 발생할 수 있으므로 Task, Load Balancer, dependency의 AZ 구조를 이해한다. 비용 때문에 단일 AZ로 축소해 가용성을 훼손하지 않는다.

## 로그와 ECR 정리

- Log Group retention을 명시한다.
- 불필요한 debug 로그와 고카디널리티 필드를 조정한다.
- ECR Lifecycle Policy로 오래된 untagged/dev 이미지를 정리한다.
- 롤백에 필요한 release 이미지는 보존한다.
- Lifecycle Policy preview로 영향을 확인한다.

## 실무 적용: 운영 최적화

- IaC로 Cluster, Service, Role, Alarm 설정을 재현한다.
- 배포와 장애 대응 runbook을 유지한다.
- 이미지와 Task Definition revision을 추적 가능하게 연결한다.
- Service quota와 subnet IP를 정기적으로 확인한다.
- 비용 태그와 Cost Explorer/예산 Alarm을 활용한다.
- 정기적으로 사용하지 않는 Service, Target Group, NAT 경로를 검토한다.

## 시험 포인트

- 중단 가능한 무상태 작업의 비용 절감: Spot
- 오래된 이미지 자동 삭제: ECR Lifecycle Policy
- 오래된 로그 비용 제어: CloudWatch Logs retention
- 과도한 Fargate 비용: 지표 기반 right sizing
- EC2의 낮은 사용률: bin packing, 인스턴스 크기/수, Capacity Provider 검토
- 비용 최저만 보고 Multi-AZ나 최소 안정 용량을 제거하지 않는다.

## 연습문제

**문제.** 재시도 가능한 SQS worker의 비용을 줄이되 API Service의 안정성은 유지해야 한다. 가장 적절한 방식은?

**정답:** API의 안정 용량은 온디맨드로 유지하고, 중단을 견디는 worker 또는 추가 worker 용량에 Fargate Spot을 사용한다. 메시지 처리는 idempotent하게 설계한다.
