# 연관관계 매핑 기초

연관관계 매핑은 테이블의 외래 키 관계를 Java 객체의 참조 관계로 표현하는
방법입니다. `Member`가 소속된 `Team`을 객체로 다룰 수 있게 하지만, 실제 저장은
여전히 외래 키를 가진 테이블에서 이루어집니다.

테이블 구조와 객체 관계의 방향이 다를 수 있다는 점을 이해해야, 데이터가 저장되지
않는 문제와 불필요한 조회 문제를 피할 수 있습니다.

## 객체 참조와 외래 키

관계형 데이터베이스는 `member.team_id`처럼 외래 키 값으로 관계를 저장합니다.
반면 Java 객체는 `member.getTeam()`처럼 다른 객체를 참조합니다. JPA 연관관계
매핑은 이 둘을 연결하는 규칙입니다.

회원 여러 명이 하나의 팀에 소속되는 구조라면, 외래 키는 여러 회원 행이 있는
`members` 테이블에 둡니다.

```text
teams                         members
-----                         ----------------
id                            id
name                          name
                              team_id  -> teams.id
```

객체에서는 `Member`가 `Team`을 알게 하는 단방향 관계부터 시작하는 편이 쉽고
안전합니다. 반대로 `Team`이 회원 목록을 반드시 알아야 할 때만 양방향 관계를
추가합니다.

## `@ManyToOne`으로 회원과 팀 연결하기

회원은 하나의 팀에 소속되고, 한 팀에는 여러 회원이 소속될 수 있습니다. 이때
`Member` 쪽에 `@ManyToOne`과 `@JoinColumn`을 선언합니다.

```java
@Entity
@Table(name = "members")
public class Member {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "team_id", nullable = false)
    private Team team;

    protected Member() {
    }

    public Member(Team team) {
        changeTeam(team);
    }

    void changeTeam(Team team) {
        this.team = team;
    }
}
```

`@ManyToOne`은 많은 `Member`가 하나의 `Team`을 참조한다는 뜻입니다.
`@JoinColumn(name = "team_id")`는 `members.team_id` 외래 키 컬럼을 사용한다고
명시합니다. `optional = false`와 `nullable = false`는 팀 없는 회원을 허용하지
않는다는 객체·DB 규칙을 함께 나타냅니다.

### 잘못된 예: 연관된 엔티티에 `@Column` 사용하기

```java
@Column(name = "team_id")
private Team team;
```

`@Column`은 `String`, `Long` 같은 기본값을 하나의 컬럼에 저장할 때 사용합니다.
`Team`은 별도 테이블을 가진 엔티티이므로, 이 코드만으로는 외래 키 관계를 표현할
수 없습니다.

### 올바른 예: 관계와 외래 키 컬럼을 함께 선언하기

```java
@ManyToOne(fetch = FetchType.LAZY, optional = false)
@JoinColumn(name = "team_id", nullable = false)
private Team team;
```

JPA는 이 선언을 바탕으로 `Member.team` 객체 참조와 `members.team_id` 컬럼을
연결합니다. 실제 컬럼 이름, NOT NULL 제약 조건, 외래 키 제약 조건은 운영 스키마와
마이그레이션 파일에서 반드시 확인합니다.

### 실무 예시: `teamId`로 쓰고 `team`은 읽기만 하기

명령 요청이나 배치 작업이 팀 객체 전체가 아니라 팀 식별자만 받는 경우가 많습니다.
이때 매번 `Team`을 조회해 연관관계를 바꾸는 것보다 `teamId`를 바로 저장하는 편이
코드와 SQL을 단순하게 만들 수 있습니다. `team`은 필요한 화면이나 비즈니스 로직에서
읽기 위해 남겨 둘 수 있습니다.

```java
@Column(name = "team_id", nullable = false)
private Long teamId;

@ManyToOne(fetch = FetchType.LAZY)
@JoinColumn(
    name = "team_id",
    insertable = false,
    updatable = false
)
private Team team;

public void changeTeamId(Long teamId) {
    this.teamId = teamId;
}
```

이 예시에서는 `teamId`가 `members.team_id`를 INSERT와 UPDATE SQL에 포함하는
쓰기 필드입니다. `team`은 같은 컬럼을 읽기만 하므로 `member.changeTeamId(2L)`처럼
ID만 바꿔도 저장할 수 있습니다. 팀 객체가 필요할 때 `member.getTeam()`을 호출하면
`LAZY` 설정에 따라 조회가 실행됩니다.

### 잘못된 예: 두 필드가 같은 컬럼을 함께 수정하기

```java
@ManyToOne
@JoinColumn(name = "team_id")
private Team team;

@Column(name = "team_id")
private Long teamId;
```

두 필드가 모두 같은 컬럼을 쓰도록 선언하면 JPA가 어느 값을 저장해야 할지 결정할
수 없습니다. Hibernate에서는 중복 컬럼 매핑 오류가 발생할 수 있습니다. 둘 중 하나만
쓰기 필드로 정하고, 다른 필드에는 `insertable = false, updatable = false`를 지정해야
합니다.

이 패턴의 단점도 분명합니다. `teamId`를 바꿔도 이미 로딩된 `team` 객체가 자동으로
새 팀 객체로 바뀌지는 않습니다. 같은 트랜잭션에서 두 필드를 모두 사용한다면 한쪽만
믿지 말고, 변경 후 필요한 데이터를 다시 조회하거나 객체 상태를 함께 관리합니다.
또한 존재하지 않는 ID는 저장 시 외래 키 제약 조건에서 거부되므로 입력 검증과 DB
제약 조건을 함께 둬야 합니다.

따라서 팀 ID만 전달되는 생성·수정 요청, 대량 변경, 권한 확인처럼 객체 전체가 필요
없는 작업에는 이 방식을 고려할 수 있습니다. 반대로 팀 변경 규칙이나 도메인 검증을
`Team` 객체와 함께 수행해야 한다면 앞의 `Member.team` 연관관계를 쓰는 편이 더
명확합니다. 프로젝트 안에서는 한 엔티티의 외래 키 쓰기 방식을 하나로 정하고,
개발자가 `team`과 `teamId` 중 어느 필드를 변경해야 하는지 이름과 메서드로 분명히
알려야 합니다.

## 연관관계의 주인

양방향 관계에서는 두 객체가 서로를 참조합니다. 하지만 DB의 외래 키는 하나이므로,
JPA는 외래 키를 변경할 한쪽을 연관관계의 주인으로 정해야 합니다.

이 예시에서는 `members.team_id`를 가진 `Member` 쪽이 관계의 주인입니다. 앞의
기본 예시처럼 연관 필드 `team`이 쓰기 필드라면 `team`을 바꿔야 INSERT 또는 UPDATE
SQL의 외래 키 값이 바뀝니다. `teamId`를 쓰기 필드로 선택한 변형에서는
`teamId`를 바꿔야 외래 키 값이 바뀝니다.

```java
@Entity
@Table(name = "teams")
public class Team {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @OneToMany(mappedBy = "team")
    private List<Member> members = new ArrayList<>();

    protected Team() {
    }
}
```

`mappedBy = "team"`은 이 목록이 `Member`의 `team` 필드로 매핑된 관계의 반대쪽임을
뜻합니다. `mappedBy`에는 DB 컬럼명인 `team_id`가 아니라 주인 엔티티의 필드명
`team`을 적습니다.

### 잘못된 예: 반대쪽 목록만 변경하기

```java
team.getMembers().add(member);
```

이 코드는 메모리의 목록만 바꾸고, 주인인 `member.team`은 바꾸지 않습니다. 따라서
JPA가 외래 키를 변경하지 않아 저장 결과와 객체 상태가 달라질 수 있습니다.

### 올바른 예: 주인을 변경하고 양쪽 객체를 맞추기

```java
public void addMember(Member member) {
    members.add(member);
    member.changeTeam(this);
}
```

서비스 코드에서는 `team.addMember(member)`처럼 이 메서드만 호출합니다. 주인인
`Member`를 변경하므로 외래 키가 저장되고, `Team.members`도 함께 갱신되어 같은
트랜잭션 안에서 객체 상태를 믿고 사용할 수 있습니다.

기존 팀에서 회원을 옮기는 기능이라면 이전 팀의 목록에서도 제거해야 합니다. 이
작업을 빼먹지 않도록 관계 변경 메서드를 한 곳에 두는 것이 실무에서 안전합니다.

## 양방향 관계를 안전하게 다루기

양방향 관계는 조회 코드를 편하게 만들 수 있지만, 항상 필요한 것은 아닙니다.
`Team`에서 회원 목록을 탐색할 요구가 없다면 `Member -> Team` 단방향만으로 충분합니다.

처음부터 모든 관계를 양방향으로 만들면 어느 쪽이 주인인지 혼동하기 쉽고, JSON
응답으로 엔티티를 그대로 반환할 때 순환 참조 문제도 생길 수 있습니다. API 응답은
엔티티 대신 필요한 값만 담은 DTO로 변환합니다.

`@OneToOne`, `@ManyToMany`도 JPA가 제공하는 관계이지만, 관계의 외래 키 위치와
업무 규칙을 먼저 설계해야 합니다. 특히 `@ManyToMany`는 중간 테이블에 생성일,
상태 같은 업무 컬럼이 필요한 경우가 많습니다. 실무에서는 그 중간 테이블을 별도
엔티티로 만드는 설계를 자주 선택합니다.

## 로딩 전략의 출발점

JPA 표준에서 `@ManyToOne`의 기본 로딩 전략은 `EAGER`입니다. 그러나 회원을
조회할 때마다 팀이 항상 필요한 것은 아니므로, 실무에서는 필요한 시점에 팀을
가져오도록 `fetch = FetchType.LAZY`를 명시하는 경우가 많습니다.

`LAZY`는 연관 객체를 처음 사용할 때 조회를 시도할 수 있다는 힌트입니다. 실제
동작 방식은 JPA 구현체와 설정에 따라 다릅니다. Hibernate는 보통 프록시를 이용해
지연 로딩을 구현하지만, 프록시 세부 동작을 JPA 표준 규칙으로 일반화하면 안 됩니다.

트랜잭션이 끝난 뒤 지연 로딩 필드에 접근하면 예외가 발생할 수 있습니다. 필요한
데이터는 조회 목적에 맞게 트랜잭션 안에서 가져오고 DTO로 변환합니다. 여러 건을
조회할 때 발생할 수 있는 N+1 문제와 조회 최적화는 다음 문서에서 다룹니다.

## 실무에서 먼저 정할 기준

- **DB 외래 키가 있는 테이블 쪽을 기준으로 주인을 정하고**, 생성되는 SQL을 확인합니다.
- 단방향 `@ManyToOne`부터 시작하고, 실제 탐색 요구가 생길 때만 양방향을 추가합니다.
- 연관관계 변경은 한 메서드로 감싸 객체 양쪽 상태와 외래 키 상태를 함께 맞춥니다.
- 엔티티를 API 응답에 바로 반환하지 않고 DTO를 사용해 순환 참조와 조회 범위를
  통제합니다.
- `EAGER`를 성능 해결책으로 선택하지 않습니다. 필요한 연관 데이터를 조회마다
  명확하게 설계합니다.

연관관계 매핑은 객체 탐색을 편하게 해 주지만 SQL을 대신 설계해 주지는 않습니다.
운영 환경에서는 외래 키 제약, 인덱스, 실제 JOIN과 조회 횟수를 함께 검토해야 합니다.
