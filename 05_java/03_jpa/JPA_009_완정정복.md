# JPA 완전 정복

Spring Data JPA는 반복적인 데이터 접근 코드를 줄여 주지만, repository 메서드 하나가 조회 성능과
도메인 규칙까지 보장하지는 않습니다. 이 문서는 `Member`와 `Product`를 예시로, 조회 목적에 맞는 JPA
기능 선택과 자주 발생하는 문제를 정리합니다.

## Spring Data JPA 기초

`JpaRepository`는 기본 CRUD와 페이징 기능을 제공합니다. ID 조회, 존재 여부 확인, 단순 조건 검색처럼
의도가 짧게 드러나는 경우에 적합합니다.

```java
public interface MemberRepository extends JpaRepository<Member, Long> {

    Optional<Member> findByEmail(String email);

    boolean existsByEmail(String email);

    Page<Member> findByStatus(MemberStatus status, Pageable pageable);
}
```

`existsByEmail()`은 중복 확인의 사용자 경험에는 도움이 되지만, 동시 요청까지 막지는 못합니다.
`members.email`에는 반드시 UNIQUE 제약 조건을 둬야 합니다.

| 상황                   | 우선 선택       | 주의할 점                               |
| ---------------------- | --------------- | --------------------------------------- |
| ID·단일 조건 조회      | 쿼리 메서드     | 이름이 길어지면 조건을 숨기지 않습니다. |
| 고정된 JOIN·DTO 조회   | `@Query`의 JPQL | 엔티티명과 필드명을 사용합니다.         |
| DB 전용 함수·특수 문법 | native SQL      | DB 이식성과 count 쿼리를 확인합니다.    |
| 선택 조건이 많음       | QueryDSL        | 별도 조회 repository로 분리합니다.      |

다음처럼 조건이 길어진 메서드는 유지보수하기 어렵습니다.

```java
Page<Member> findByNameContainingAndStatusAndCreatedAtBetween(
    String name,
    MemberStatus status,
    LocalDateTime from,
    LocalDateTime to,
    Pageable pageable
);
```

목록 API에서 필요한 필드만 있다면 엔티티보다 DTO를 조회합니다. 엔티티를 그대로 반환하면 내부 필드 노출, 지연
로딩, JSON 순환 참조가 함께 따라올 수 있습니다.

```java
public record MemberSummary(Long id, String name, MemberStatus status) {
}

@Query("""
    select new com.example.member.MemberSummary(m.id, m.name, m.status)
    from Member m
    where m.status = :status
""")
Page<MemberSummary> findSummariesByStatus(
    @Param("status") MemberStatus status,
    Pageable pageable
);
```

`Page`는 전체 건수를 위한 count 쿼리를 보통 추가로 실행합니다. 다음 페이지 존재 여부만 필요한 무한
스크롤이라면 `Slice`가 더 적합할 수 있습니다.

## Entity 설계와 연관관계

엔티티는 테이블 복사본이 아니라 상태와 규칙을 가진 객체입니다. 생성과 변경의 유효성 검사는 생성 메서드나
도메인 메서드에 모으고, setter를 공개하지 않습니다.

```java
@Entity
@Table(name = "products")
public class Product {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 100)
    private String name;

    @Column(nullable = false)
    private int price;

    protected Product() {
    }

    public Product(String name, int price) {
        if (price < 0) {
            throw new IllegalArgumentException("가격은 음수일 수 없습니다.");
        }
        this.name = name;
        this.price = price;
    }

    public void changePrice(int price) {
        if (price < 0) {
            throw new IllegalArgumentException("가격은 음수일 수 없습니다.");
        }
        this.price = price;
    }
}
```

회원이 상품을 등록하는 예시에서는 외래 키를 가진 `Product.member`가 연관관계의 주인입니다. 반대쪽 컬렉션은
탐색이 실제로 필요할 때만 둡니다.

```java
@Entity
@Table(name = "products")
public class Product {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "member_id", nullable = false)
    private Member member;

    public void assignSeller(Member member) {
        this.member = member;
    }
}

@Entity
@Table(name = "members")
public class Member {

    @OneToMany(mappedBy = "member")
    private List<Product> products = new ArrayList<>();
}
```

`@ManyToOne`과 `@OneToOne`의 JPA 기본 로딩은 EAGER입니다. 기본값에 의존하지 말고 `LAZY`를
명시합니다. EAGER는 모든 화면에서 JOIN 한 번을 보장하지 않으며, 불필요한 조회와 N+1의 원인이 될 수
있습니다.

다대다 관계는 중간 테이블에 생성 시각, 정렬 순서, 상태 같은 속성이 필요해지는 경우가 많습니다.
`@ManyToMany`보다 연결 테이블을 별도 엔티티로 모델링합니다.

`cascade = ALL`과 `orphanRemoval = true`는 부모와 자식의 생명주기가 항상 같을 때만
사용합니다. 독립적으로 관리하거나 보관해야 하는 `Product`에 회원 삭제를 전파하면 의도하지 않은 데이터 삭제가 생길
수 있습니다.

## N+1 문제와 해결

상품 목록을 조회한 뒤 판매자 이름을 읽는 상황을 보겠습니다. 상품 N개를 읽고, 각 상품의 판매자를 초기화하려고 N번 더
조회하면 N+1 문제가 생깁니다.

```java
List<Product> products = productRepository.findAll();

for (Product product : products) {
    log.info("{}", product.getMember().getName());
}
```

N+1은 LAZY 자체의 오류가 아닙니다. 한 요청에서 실제로 필요한 연관 데이터를 명시하지 않았을 때 나타나는 조회 계획
문제입니다. SQL 로그와 요청당 쿼리 수를 확인한 뒤 해결 방법을 고릅니다.

### fetch join: 관계가 적고 결과 전체가 필요한 경우

```java
@Query("""
    select p
    from Product p
    join fetch p.member
    where p.status = :status
""")
List<Product> findWithSellerByStatus(@Param("status") ProductStatus status);
```

상품과 판매자를 한 SQL로 가져와야 하는 상세·소규모 목록에 적합합니다. 다만 `@OneToMany` 컬렉션 fetch
join에 페이징을 조합하면 행이 불어나 DB 페이징이 깨질 수 있습니다. 대량 목록에서 컬렉션을 fetch join으로
모두 가져오지 않습니다.

### EntityGraph: 단순 repository 메서드의 조회 범위 표현

```java
@EntityGraph(attributePaths = "member")
List<Product> findByStatus(ProductStatus status);
```

간단한 연관관계만 함께 가져오는 경우에는 읽기 쉽습니다. 복잡한 조인 조건, 집계, DTO 변환이 필요하면 JPQL 또는
QueryDSL이 더 명확합니다.

### 배치 조회: 페이징하면서 연관 데이터를 읽는 경우

```yaml
spring:
  jpa:
    properties:
      hibernate:
        default_batch_fetch_size: 100
```

- 배치 크기를 설정하면 지연 로딩 대상 ID를 `IN (...)` 조건으로 묶어 조회합니다.
- 컬렉션 페이징과 함께 쓸 수 있어 실무 목록 조회에 자주 사용합니다.
- 크기는 100으로 고정할 값이 아니며, DB의 파라미터 제한과 실제 조회량을 측정해 정합니다.

### default_batch_fetch_size 값의 의미

`default_batch_fetch_size`는 한 번의 지연 로딩 SQL에서 함께 초기화할 수 있는 엔티티 프록시 또는
컬렉션의 **최대 개수**입니다.

페이지 크기, JDBC fetch size, INSERT·UPDATE JDBC 배치 크기를 뜻하지 않습니다.

예를 들어 상품 250개를 페이지로 조회한 뒤 각 상품의 판매자 `Member`를 사용할 때, 값을 100으로 설정했다면
Hibernate는 현재 영속성 컨텍스트에 있는 미초기화 프록시의 식별자 중 최대 100개를 묶어 조회할 수 있습니다.

```sql
-- 첫 Product에서 member를 처음 접근할 때의 예시입니다.
select m.id, m.name
from members m
where m.id in (?, ?, ..., ?); -- 최대 100개 ID
```

250개의 서로 다른 판매자를 모두 읽는다면 추가 쿼리 수는 데이터와 DB dialect에 따라 달라지지만, 이상적인 경우
N번 대신 대략 세 묶음이 됩니다.

이미 영속성 컨텍스트에 있거나 2차 캐시에서 찾은 `Member`, 같은 판매자를 공유한 여러 `Product`는 추가
SQL의 대상이 아닙니다. 따라서 `ceil(250 / 100)`처럼 기계적으로 쿼리 수를 단정하지 않습니다.

이 전역 설정은 개별 `@BatchSize`가 없는 엔티티와 컬렉션의 기본값으로 사용합니다.

특정 관계만 다른 값이 필요하면 해당 매핑에 `@BatchSize(size = 20)`처럼 명시할 수 있습니다.
`@BatchSize`와 이 설정은 JPA 표준이 아닌 Hibernate 기능입니다.

```java
@OneToMany(mappedBy = "member")
@BatchSize(size = 20)
private List<Product> products = new ArrayList<>();
```

값을 크게 잡는다고 항상 좋아지지는 않습니다. 한 번에 전달하는 ID 수와 결과 행이 커져 DB 파라미터 제한, SQL
파싱 비용, 메모리 사용량에 영향을 줄 수 있습니다.

반대로 너무 작으면 N+1을 충분히 줄이지 못합니다. 목록 페이지 크기, 연관 데이터의 평균 크기, DB 제한을 기준으로
후보 값을 정하고 SQL 로그와 부하 테스트로 검증합니다.

`default_batch_fetch_size`는 fetch join을 대체하지 않습니다. 이번 요청에서 반드시 함께
필요한 ToOne 관계는 fetch join 또는 `EntityGraph`가 더 예측 가능할 수 있습니다.

반면 컬렉션을 포함한 페이징 목록에서는 ID 조회 뒤 배치 로딩이 더 안전한 선택이 될 수 있습니다.

## QueryDSL

QueryDSL은 Q 타입을 사용해 Java 코드에서 타입 안전한 쿼리를 만듭니다. 검색 조건이 선택적으로 결합되거나,
JOIN과 DTO 조회가 복잡할 때 장점이 큽니다. 단순 CRUD까지 모두 QueryDSL로 작성하면 오히려 코드가
늘어납니다.

Spring Boot 3 계열에서는 Jakarta 호환 QueryDSL 의존성과 annotation processor를
사용합니다. 정확한 의존성 구성은 사용하는 Gradle, QueryDSL, Spring Boot 버전의 공식 문서를
확인합니다.

```java
@Configuration
public class QuerydslConfig {

    @Bean
    JPAQueryFactory jpaQueryFactory(EntityManager entityManager) {
        return new JPAQueryFactory(entityManager);
    }
}
```

```java
@Repository
@RequiredArgsConstructor
public class ProductQueryRepository {

    private final JPAQueryFactory queryFactory;

    public List<ProductSummary> search(ProductSearchCondition condition) {
        QProduct product = QProduct.product;
        QMember member = QMember.member;

        return queryFactory
            .select(Projections.constructor(
                ProductSummary.class,
                product.id,
                product.name,
                product.price,
                member.name
            ))
            .from(product)
            .join(product.member, member)
            .where(
                nameContains(product, condition.name()),
                priceGoe(product, condition.minPrice()),
                sellerIdEq(product, condition.sellerId())
            )
            .orderBy(product.id.desc())
            .fetch();
    }

    private BooleanExpression nameContains(QProduct product, String name) {
        return StringUtils.hasText(name) ? product.name.contains(name) : null;
    }

    private BooleanExpression priceGoe(QProduct product, Integer price) {
        return price != null ? product.price.goe(price) : null;
    }

    private BooleanExpression sellerIdEq(QProduct product, Long sellerId) {
        return sellerId != null ? product.member.id.eq(sellerId) : null;
    }
}
```

`where()`는 `null` 조건을 무시하므로 작은 조건 메서드를 조합하기 좋습니다. 반환 타입을 엔티티와 DTO 중
무엇으로 할지 먼저 정해야 합니다. API 조회는 DTO를, 상태 변경은 영속 엔티티를 사용하는 경계를 유지합니다.

## 성능 최적화

성능 최적화는 어노테이션을 많이 붙이는 일이 아니라, 실제 SQL과 실행 계획을 보고 필요한 데이터만 읽는 일입니다. 먼저
느린 요청의 쿼리 수, 실행 시간, 반환 행 수를 측정합니다.

목록과 검색 API는 DTO 직접 조회가 적합한 경우가 많습니다. 반면 변경할 엔티티를 DTO로 조회한 뒤 다시 저장하는
방식은 변경 감지와 도메인 규칙을 우회하므로 적합하지 않습니다.

```java
@Transactional(readOnly = true)
public Page<ProductSummary> findProducts(ProductSearchCondition condition) {
    return productQueryService.findPage(condition);
}
```

읽기 전용 트랜잭션은 조회 의도를 드러내며 Hibernate 설정에 따라 스냅샷 관리 비용을 줄일 수 있습니다. 항상 큰
성능 향상을 보장하지 않으므로 측정 없이 만능 해결책으로 사용하지 않습니다.

벌크 update와 delete는 영속성 컨텍스트를 거치지 않고 DB에 바로 반영합니다.

```java
@Modifying(clearAutomatically = true, flushAutomatically = true)
@Query("""
    update Product p
    set p.status = :targetStatus
    where p.member.id = :memberId
""")
int changeProductStatus(
    @Param("memberId") Long memberId,
    @Param("targetStatus") ProductStatus targetStatus
);
```

이미 메모리에 있는 `Product`는 이전 상태일 수 있습니다. 같은 트랜잭션에서 엔티티를 계속 사용한다면
`clearAutomatically` 또는 명시적 `EntityManager.clear()`가 필요한지 검토합니다.

인덱스는 자주 실행되는 조건·정렬·JOIN을 대상으로 실행 계획을 근거로 설계합니다. `member_id`,
`status`를 늘 함께 조건으로 사용한다고 해서 모든 조합의 인덱스를 추가하면 쓰기 비용과 저장 공간도 증가합니다.

## 실전 패턴

### 역할에 따라 repository를 나눕니다

기본 저장과 간단한 조회는 Spring Data repository에 두고, 검색·통계·목록 DTO처럼 복잡한 읽기는 별도
query repository로 분리합니다.

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    Optional<Product> findByIdAndMemberId(Long productId, Long memberId);
}

public interface ProductQueryRepository {

    Page<ProductSummary> search(ProductSearchCondition condition,
                                Pageable pageable);
}
```

이 분리는 CQRS를 강제하는 규칙이 아닙니다. 단순 서비스까지 인터페이스와 구현체를 과도하게 늘리지 말고, 읽기 복잡도가
커지는 시점에 적용합니다.

### 감사 필드는 공통 기반 엔티티로 관리합니다

```java
@MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseTimeEntity {

    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdAt;

    @LastModifiedDate
    private LocalDateTime updatedAt;
}
```

생성·수정 시각처럼 여러 엔티티에 공통인 값에 적합합니다. `@EnableJpaAuditing` 설정과 테스트 환경에서도
값이 채워지는지 확인합니다. 생성자나 서비스에서 시간을 직접 덮어쓰는 규칙과 섞으면 책임이 모호해집니다.

### 동시 수정은 데이터 성격에 맞춰 제어합니다

- 재고처럼 같은 행을 동시에 변경할 수 있는 데이터에는 `@Version` 기반 낙관적 락을 우선 검토합니다.
- 충돌이 드물면 DB 행을 오래 잠그지 않아 처리량에 유리합니다.
- 충돌 시 재시도와 사용자 응답을 함께 설계해야 합니다. 충돌이 빈번하고 작업 시간이
  짧을 때만 비관적 락을 검토합니다.
- 자세한 기준은 [트랜잭션과 동시성 제어](JPA_007_트랜잭션과%20동시성%20제어.md)를 참고합니다.

## 정리 및 베스트 프랙티스

- 단순 CRUD와 짧은 조건은 `JpaRepository`와 쿼리 메서드를 사용합니다.
- 목록 API는 엔티티 반환보다 DTO 직접 조회를 우선 검토합니다.
- 모든 연관관계의 로딩 전략을 `LAZY`로 명시하고, 필요한 조회에서만 fetch join,
  EntityGraph, 배치 조회를 선택합니다.
- 컬렉션 fetch join과 페이징을 함께 사용하지 않습니다. ID 페이징과 배치 조회 또는
  DTO 조회로 나눕니다.
- 동적 조건과 복잡한 조합은 QueryDSL로 분리하되, 단순 쿼리까지 일괄 전환하지
  않습니다.
- 벌크 연산 뒤에는 영속성 컨텍스트와 DB의 상태 차이를 확인합니다.
- 인덱스와 `readOnly` 설정은 실제 SQL, 실행 계획, 부하 측정 결과를 근거로 적용합니다.
- 엔티티 변경은 트랜잭션 안에서 도메인 메서드로 처리하고, API에 엔티티를 직접
  노출하지 않습니다.
