# 트랜잭션과 동시성 제어

JPA의 영속성 컨텍스트는 객체 변경을 SQL로 바꿔 주지만, 동시에 들어온 요청의
업무 규칙까지 자동으로 지켜 주지는 않습니다. 이 문서에서는 Spring 트랜잭션의
경계와 JPA 표준 락을 구분하고, 충돌 빈도와 데이터 정합성에 맞는 제어 방법을
설명합니다.

## 트랜잭션 경계와 전파

트랜잭션은 여러 SQL 작업을 모두 성공시키거나 모두 취소하는 업무 단위입니다.
Spring의 `@Transactional`은 프록시를 통해 메서드 전후에 트랜잭션을 열고,
정상 종료 시 커밋하거나 규칙에 맞는 예외가 나면 롤백합니다. 이는 Spring의
기능이며 JPA 표준 어노테이션이 아닙니다.

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;

    @Transactional
    public void cancel(Long orderId) {
        Order order = orderRepository.findById(orderId).orElseThrow();
        order.cancel();
    }
}
```

기본 전파 방식인 `Propagation.REQUIRED`는 기존 트랜잭션이 있으면 참여하고,
없으면 새 트랜잭션을 만듭니다. 대부분의 서비스 메서드에는 이것이 적절합니다.

| 전파 방식      | 동작                                               | 사용할 때의 주의점                          |
| -------------- | -------------------------------------------------- | ------------------------------------------- |
| `REQUIRED`     | 기존 트랜잭션에 참여하거나 새로 만듭니다.          | 기본값이며 일반 업무 처리의 기준입니다.     |
| `REQUIRES_NEW` | 기존 트랜잭션을 보류하고 독립 트랜잭션을 만듭니다. | 커넥션을 추가로 사용하며 결과가 분리됩니다. |
| `MANDATORY`    | 기존 트랜잭션이 없으면 예외를 냅니다.              | 상위 업무 단위 안에서만 실행할 때 씁니다.   |
| `NESTED`       | 지원될 때 savepoint를 사용합니다.                  | 트랜잭션 매니저와 DB 지원을 확인합니다.     |

### 잘못된 예

```java
@Transactional
public void placeOrder(PlaceOrderCommand command) {
    orderRepository.save(Order.create(command));
    auditService.writeAudit(command); // REQUIRES_NEW
    paymentClient.pay(command);
}

// auditService
@Transactional(propagation = Propagation.REQUIRES_NEW)
public void writeAudit(PlaceOrderCommand command) {
    // 감사 로그 저장
}
```

흐름은 다음과 같습니다.

```text
1. 주문 저장 (바깥 트랜잭션, 아직 커밋 전)
2. 감사 로그 저장 (새 트랜잭션) -> 감사 로그 트랜잭션 커밋
3. 결제 호출 실패
4. 바깥 트랜잭션 롤백 → 주문 저장 취소
```

이것이 항상 잘못은 아닙니다. 예를 들어 “주문 시도가 있었고 결제에서 실패했다”에 대해서,
주문 시도라는 감사 기록을 쌓는 것이라면, 주문이 실패해도 기록을 남겨야 하므로 REQUIRES_NEW가
적절할 수 있습니다.

하지만 감사 로그의 의미가 **주문이 성공했다 라면** 잘못(❌) 입니다. 주문이 실제로는
롤백되었는데 성공 로그가 남아 데이터가 서로 모순되기 때문입니다.

추가로 중요한 문제가 있습니다.

- 바깥 트랜잭션에서 저장한 주문은 아직 커밋되지 않았습니다.
- 따라서 새 트랜잭션인 writeAudit()는 그 주문 데이터를 일반적으로 조회할 수 없습니다.
- 감사 로그가 주문 FK를 참조하면, 주문이 아직 보이지 않아 FK 제약 조건 오류가 날 수도 있습니다.
- FK 참조를 하지 않는다면, 주문 생성 감사 로그가 쌓이고, 주문은 롤백되었는데 성공 로그가 남아 데이터가 모순
  될 수도 있습니다.
- 또한, 요청 하나가 DB 커넥션을 두 개까지 점유할 수 있습니다. 동시 요청이 많고 커넥션 풀이 작으면 커넥션
  부족 위험도 커집니다.

### 올바른 예: 업무 원자성에 맞춰 기본 전파를 사용하기

```java
@Transactional
public void placeOrder(PlaceOrderCommand command) {
    Order order = Order.create(command);
    orderRepository.save(order);
    order.addAudit("ORDER_CREATED");
}
```

- `주문`과 `주문 성공 감사`가 함께 성공해야 한다면 같은 트랜잭션으로 묶습니다.
- 외부 결제, 메시지 발행, 이메일은 DB 트랜잭션 안에서 오래 기다리지 않습니다.
- 커밋 뒤 처리할 작업은 outbox와 재처리 전략처럼 실패를 복구할 수 있는 설계를 별도로 둡니다.

## 격리 수준과 JPA의 범위

격리 수준은 한 트랜잭션이 다른 미완료·완료 트랜잭션의 변경을 어느 정도 볼 수
있는지 정하는 데이터베이스 기능입니다. Spring의 `isolation` 속성은 새로 만드는
트랜잭션에 격리 수준을 요청하지만, 실제 지원 범위와 기본 값은 DB·드라이버에
따라 다릅니다.

JPA는 격리 수준을 표준화하지 않습니다. 영속성 컨텍스트의 1차 캐시 때문에 같은
트랜잭션에서 같은 엔티티를 다시 `find()`하면 DB를 다시 읽지 않고 관리 중인 객체를
반환할 수 있습니다. 이를 DB의 `REPEATABLE_READ`와 동일하다고 해석하면 안 됩니다.

높은 격리 수준만으로 모든 업무 충돌을 해결하려 하지 않습니다. 필요한 행에
낙관적 락·비관적 락·조건부 UPDATE를 적용하고, 유일성·참조 무결성·범위 검증은
DB 제약 조건으로 최종 보장하는 편이 예측하기 쉽습니다.

## 잃어버린 갱신 문제

두 요청이 재고 10을 동시에 읽고 각각 1을 빼면, 둘 다 9를 저장하여 한 번의
차감이 사라질 수 있습니다. 기본적인 "조회 후 객체 변경"은 충돌을 감지하지
못합니다.

### 잘못된 예: 버전·락 없이 읽고 수정하기

```java
@Transactional
public void decreaseStock(Long productId, int quantity) {
    Product product = productRepository.findById(productId).orElseThrow();
    product.decrease(quantity);
}
```

이 코드만으로는 두 트랜잭션이 같은 값을 읽는 일을 막지 못합니다. 데이터베이스의
기본 격리 수준, SQL 실행 순서, 엔티티 매핑에 따라 결과가 달라질 수 있으며, 재고가
음수가 되는 조건도 별도로 검증해야 합니다.

## 낙관적 락: 버전을 비교하기

낙관적 락은 충돌이 드물다고 보고 DB 행을 미리 잠그지 않습니다. 대신 읽을 때의
버전을 UPDATE 또는 DELETE 때 확인합니다. JPA 표준에서는 `@Version`으로 버전
필드나 속성을 지정합니다.

```java
@Entity
public class Product {

    @Id
    private Long id;

    @Version
    private Long version;

    private int stock;

    public void decrease(int quantity) {
        if (stock < quantity) {
            throw new IllegalStateException("재고가 부족합니다.");
        }
        stock -= quantity;
    }
}
```

JPA 제공자는 버전이 있는 엔티티를 갱신할 때 메모리 버전과 DB 버전을 비교해야 합니다.
일치하지 않으면 `OptimisticLockException`을 던지고 현재 트랜잭션을
롤백 대상으로 표시합니다. Hibernate가 만드는 SQL의 정확한 모양은 구현체와
매핑에 따라 다르지만, 보통 다음과 같은 조건이 포함됩니다.

```sql
update product
set stock = ?, version = ?
where id = ? and version = ?
```

### 잘못된 예: 실패한 트랜잭션 안에서 재시도하기

```java
@Transactional
public void decreaseWithRetry(Long productId, int quantity) {
    for (int attempt = 0; attempt < 3; attempt++) {
        try {
            decrease(productId, quantity);
            return;
        } catch (OptimisticLockException exception) {
            // 같은 영속성 컨텍스트에서 다시 시도합니다.
        }
    }
}
```

- 낙관적 락 충돌 뒤 현재 트랜잭션은 롤백 전용 상태일 수 있습니다.
- 같은 영속성 컨텍스트에는 오래된 엔티티도 남아 있을 수 있으므로, 이 상태에서 재시도하면
  성공처럼 보여도 커밋에서 실패하거나 오래된 상태를 다시 사용할 위험이 있습니다.

### 올바른 예: 새 트랜잭션으로 제한된 재시도하기

```java
@Service
@RequiredArgsConstructor
public class StockRetryService {

    private final StockCommandService stockCommandService;

    public void decrease(Long productId, int quantity) {
        for (int attempt = 0; attempt < 3; attempt++) {
            try {
                stockCommandService.decreaseOnce(productId, quantity);
                return;
            } catch (OptimisticLockingFailureException exception) {
                // 다음 반복은 별도 Spring 빈의 새 트랜잭션으로 실행됩니다.
            }
        }
        throw new IllegalStateException("동시 요청이 많아 재시도에 실패했습니다.");
    }
}
```

`decreaseOnce()`를 별도 Spring 빈의 `@Transactional` 메서드로 두면 반복마다
새 영속성 컨텍스트와 트랜잭션을 사용합니다.

Spring은 JPA의 `OptimisticLockException`을 `OptimisticLockingFailureException` 계열로
변환할 수 있습니다. 변환 예외의 정확한 타입은 사용하는 데이터 접근 계층을 확인합니다.

재시도 횟수, 짧은 backoff, 최종 사용자 응답은 업무 특성에 맞게 정합니다. 결제나
쿠폰 발급처럼 외부 부수 효과가 있는 작업은 무작정 재시도하지 말고 멱등 키와
처리 상태를 함께 설계해야 합니다.

## 비관적 락: DB 행을 잠그기

비관적 락은 충돌 가능성이 높거나 늦은 충돌 실패를 감당하기 어려울 때, 트랜잭션이
끝날 때까지 DB 행의 장기 락을 얻는 방식입니다. JPA 표준의 `LockModeType.PESSIMISTIC_WRITE`를
사용할 수 있습니다.

타임아웃 힌트의 준수 여부도 DB와 제공자에 따라 달라지므로, 애플리케이션의 요청 타임아웃과 DB lock timeout을
함께 설정하고 부하 테스트로 확인합니다.

```java
public interface ProductRepository extends JpaRepository<Product, Long> {

    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("select p from Product p where p.id = :id")
    Optional<Product> findByIdForUpdate(@Param("id") Long id);
}
```

```java
@Transactional
public void decreaseWithLock(Long productId, int quantity) {
    Product product = productRepository.findByIdForUpdate(productId)
        .orElseThrow(() -> new IllegalArgumentException("상품이 없습니다."));

    product.decrease(quantity);
}
```

- `@Lock`은 Spring Data JPA의 편의 기능이고, `LockModeType`은 JPA 표준입니다.
- JPA 명세는 어떤 DB SQL로 락을 얻는지 정의하지 않습니다.
- Hibernate와 DB dialect는 대개 행 잠금 SQL로 변환하지만, 실제 잠금 범위, 대기 시간, 읽기 차단 여부는
  DB격리 수준과 구현체에 따라 달라집니다. 운영 DB에서 실행 SQL과 잠금 대기 지표를 확인해야 합니다.
- 비관적 락 쿼리는 활성 트랜잭션 안에서 실행해야 합니다.
- 락을 얻지 못했을 때,
  - statement만 롤백되면 JPA는 `LockTimeoutException` 을 던집니다.
  - 트랜잭션 전체가 롤백되면 `PessimisticLockException`을 던집니다.

`findByIdForUpdate` 에서 생성되는 쿼리는, 일반적인 Hibernate + MySQL/PostgreSQL 조합에서는
아래와 유사한 SQL이 실행됩니다. 다만, 위에서 설명한 바와 같이 Hibernate와 DB dialect에 따라
컬럼·별칭·잠금 구문은 달라지며, MySQL/PostgreSQL에서는 보통 FOR UPDATE가 추가됩니다.

```sql
select
    p1_0.id,
    p1_0.name,
    p1_0.stock_quantity
from product p1_0
where p1_0.id = ?
for update
```

핵심은 SQL 끝의 FOR UPDATE입니다. 조회된 행에 쓰기 잠금을 걸고, 트랜잭션이 커밋 또는 롤백될 때까지
유지합니다. 따라서 이 메서드는 반드시 @Transactional 범위에서 호출해야 합니다.

## 재고처럼 조건 자체를 원자적으로 지키기

재고 차감은 "수량이 충분할 때만 차감한다"는 조건을 DB에서 한 번에 평가하는 방식이 더 단순하고 높은 처리량을
낼 수 있습니다.

```java
@Modifying
@Query("""
    update Product p
    set p.stock = p.stock - :quantity
    where p.id = :productId
      and p.stock >= :quantity
    """)
int decreaseIfEnough(
    @Param("productId") Long productId,
    @Param("quantity") int quantity
);
```

```java
@Transactional
public void decreaseAtomically(Long productId, int quantity) {
    int updated = productRepository.decreaseIfEnough(productId, quantity);
    if (updated != 1) {
        throw new IllegalStateException("재고가 부족하거나 상품이 없습니다.");
    }
}
```

조건부 UPDATE는 엔티티를 조회하지 않으므로 변경 감지, 도메인 콜백, `@Version`
처리와 같은 방식으로 동작하지 않습니다. 실행 뒤 같은 영속성 컨텍스트에 이미
`Product`가 있다면 값이 오래되었을 수 있으므로 `clear()`하거나 해당 엔티티를
다시 조회합니다. 이 방식은 단순 수량 갱신에 적합하며, 여러 aggregate를 함께
검증하는 복잡한 규칙을 대체하지는 않습니다.

## 데드락과 분산 환경

데드락은 두 트랜잭션이 서로 상대방이 가진 락을 기다려 진행할 수 없는 상태입니다.
DB는 보통 하나를 희생자로 선택해 롤백하지만, 애플리케이션은 그 실패를 처리해야
합니다.

- 여러 행을 잠글 때는 항상 같은 정렬 기준, 예를 들어 ID 오름차순으로 획득합니다.
- 락을 쥔 트랜잭션 안에서 외부 HTTP 호출, 파일 I/O, 긴 계산을 하지 않습니다.
- 락 대기 시간과 deadlock 오류를 관측하고, 안전한 멱등 작업에만 제한적으로
  재시도합니다.

JPA의 낙관적·비관적 락은 여러 애플리케이션 인스턴스가 같은 DB 행을 다뤄도
동작할 수 있습니다. 따라서 "서버가 여러 대면 무조건 Redis 락이 필요하다"는
말은 맞지 않습니다. 반대로 DB 밖의 공유 자원, 여러 DB·서비스를 한 작업으로
조율하거나 매우 높은 경합을 제어해야 한다면 Redis 같은 분산 락을 검토할 수
있습니다.

분산 락은 lease 만료, 소유자 검증, 장애 복구, DB 트랜잭션과의 원자성 문제가
추가됩니다. Redis 락만으로 재고 정합성을 보장한다고 가정하지 말고, DB 조건부
UPDATE나 제약 조건을 최종 방어선으로 유지합니다.

## 실무 선택 기준

| 상황                                 | 우선 검토할 방법              | 이유                                               |
| ------------------------------------ | ----------------------------- | -------------------------------------------------- |
| 일반 편집, 충돌이 드묾               | `@Version`과 제한된 재시도    | 락 대기 없이 충돌을 감지합니다.                    |
| 충돌이 잦고 짧게 끝나는 단일 행 작업 | 비관적 락                     | 늦은 충돌 실패를 줄일 수 있습니다.                 |
| 재고·잔액처럼 조건부 수치 변경       | 조건부 UPDATE와 DB 제약       | 한 SQL로 조건과 변경을 묶습니다.                   |
| 여러 서비스·외부 자원 조율           | outbox·멱등성·필요 시 분산 락 | DB 락만으로 범위를 넘는 작업을 보장할 수 없습니다. |

락은 데이터 모델과 업무 계약을 보완하는 도구입니다. 먼저 UNIQUE, NOT NULL,
CHECK, 외래 키 같은 DB 제약 조건을 두고, 실제 충돌률·응답 시간·실패 처리
요구를 측정한 뒤 가장 작은 동시성 제어 방법을 선택합니다.
