# 트랜잭션 아웃박스 패턴

아웃박스(Outbox) 패턴은 DB 변경과 “외부로 보낼 작업”을 한 트랜잭션에서 함께 기록한 뒤, 나중에 안전하게
외부 시스템으로 전달하는 방식입니다.

주문 예시라면 주문 저장과 동시에 outbox_event 테이블에도 이벤트를 저장합니다.

하나의 DB 트랜잭션

- orders 테이블: 주문 생성
- outbox_event 테이블: "주문 생성됨" 이벤트 생성
- 커밋

커밋 후 별도 워커가 outbox_event를 읽어 Kafka, 메시지 큐, 이메일 서비스, 결제 후속 처리 등에 전달합니다.

```text
주문 생성 → DB 커밋
├─ 주문 데이터
└─ 전송 대기 이벤트(outbox)
```

워커 → 대기 이벤트 전송 → 성공 표시

이 방식의 핵심은 주문은 저장됐는데 이벤트 전송이 실패하는 문제를 복구할 수 있다는 점입니다.

- 이벤트 전송 성공: 이벤트를 SENT로 표시합니다.
- 전송 실패: PENDING 상태로 남아 워커가 재시도합니다.
- 서버가 중간에 죽어도: DB에 전송 대기 기록이 남아 있으므로 다시 처리합니다.

반대로 주문 저장 후 곧바로 Kafka 전송이나 이메일 전송을 호출하면, DB 커밋 실패와
외부 전송 성공이 엇갈릴 수 있습니다. 아웃박스는 이 불일치를 줄이기 위한 패턴입니다.

단, 메시지가 중복 전송될 수 있으므로 소비 측은 이벤트 ID를 기준으로 중복 처리해도
결과가 한 번 처리한 것과 같도록(idempotent, 멱등하게) 만들어야 합니다.

## 주문 도메인에서의 사용 예

### 주문 뒤에 무엇을 비동기로 처리하는가

엔터프라이즈 쇼핑몰에서 주문 생성은 여러 후속 업무의 시작점이 됩니다. 주문 API가
모든 업무를 동기로 끝낼 필요는 없습니다. 주문이 성공했다는 사실을 이벤트로
전달하고, 각 서비스가 자기 데이터를 갱신하도록 분리할 수 있습니다.

| 이벤트 | 소비 서비스의 예 | 처리 결과의 예 |
| --- | --- | --- |
| `OrderCreated` | 결제, 재고, 배송 | 결제 승인 요청, 재고 예약, 출고 준비 생성 |
| `PaymentApproved` | 주문, 배송, 알림 | 주문 상태 변경, 배송 지시, 결제 완료 알림 |
| `PaymentFailed` | 주문, 재고, 쿠폰 | 주문 취소, 재고 예약 해제, 쿠폰 복구 |
| `OrderShipped` | 알림, 포인트, 분석 | 배송 알림, 적립 예정 처리, 판매 지표 반영 |

이 표는 하나의 가능한 분리 방식입니다. 모든 후속 처리를 Kafka로 보내야 한다는
뜻은 아닙니다. 고객에게 주문 확정 여부를 즉시 알려야 하거나, 재고를 절대
초과 판매하면 안 되는 업무는 주문 트랜잭션 안에서 조건부 SQL로 확정해야 할 수
있습니다. 반대로 비동기 재고 예약을 선택하면 주문은 `PENDING` 상태로 만들고,
예약 결과에 따라 나중에 `CONFIRMED` 또는 `CANCELLED`로 전이하는 보상 흐름이
필요합니다.

주문 생성 이벤트는 보통 `OrderCreated`이지 `PaymentApproved`가 아닙니다. 결제
승인 전 주문을 만들었다면 이벤트의 이름과 주문 상태가 이 사실을 정확히 나타내야
합니다. 이벤트 이름을 실제 업무 상태보다 낙관적으로 정하면 소비 서비스가 잘못된
후속 처리를 할 수 있습니다.

```text
주문 API
  └─ orders: PENDING 상태로 저장
  └─ outbox_event: OrderCreated.v1 저장
                         │
                         ▼
Kafka: commerce.order.created.v1 (key = orderId)
  ├─ 결제 서비스: 승인 또는 거절 이벤트 발행
  ├─ 재고 서비스: 예약 또는 예약 해제 이벤트 발행
  ├─ 배송 서비스: 결제·재고 확정 뒤 출고 준비
  ├─ 알림 서비스: 주문·결제·배송 상태별 메시지 발송
  └─ 분석 서비스: 매출·전환 지표용 읽기 모델 갱신
```

각 소비 서비스는 서로 다른 `group.id`를 사용합니다. 같은 `group.id`의 컨슈머는
작업을 나눠 처리하는 한 팀이고, 서로 다른 `group.id`는 같은 이벤트를 각자 모두
받는 별도 서비스입니다. 결제 서비스와 재고 서비스가 같은 `group.id`를 공유하면
둘 중 하나만 메시지를 처리하게 되므로 잘못된 구성입니다.

### 결제와 재고는 별도의 정합성 문제를 가집니다

결제 서비스가 `OrderCreated`를 받아 PG 승인 API를 호출하는 경우에도, 중복 이벤트
때문에 두 번 청구하면 안 됩니다. PG가 제공하는 idempotency key에는 결제 시도 ID를
사용하고, 내부 DB에는 주문별 결제 시도와 승인 결과의 유니크 제약을 둡니다. PG 승인
성공 후 서비스가 종료되어 내부 DB 기록을 못 남긴 경우에는 같은 키로 재호출하거나
PG 승인 조회 API로 결과를 복구해야 합니다.

마찬가지로 결제 서비스가 `PaymentApproved`를 저장할 때에는 결제 상태 변경과 그
이벤트의 outbox 레코드를 같은 트랜잭션으로 저장합니다. 즉, 아웃박스는 주문
서비스에서 한 번만 쓰는 기능이 아니라, DB 상태를 바꾸고 다음 서비스에 사실을
알리는 모든 서비스에 같은 방식으로 적용할 수 있습니다.

### 아웃박스 테이블 설계

다음은 PostgreSQL 기준의 예시입니다. `event_id`는 전 구간의 중복 제거 키이고,
`aggregate_id`는 Kafka 메시지 키 및 주문 단위 순서의 기준입니다. `payload`에는
필요한 이벤트 데이터만 넣고, 다른 서비스가 주문 DB를 다시 조회해야 하는 계약은
피하는 편이 안전합니다.

```sql
CREATE TABLE outbox_event (
    id              BIGSERIAL PRIMARY KEY,
    event_id        UUID NOT NULL UNIQUE,
    aggregate_type  VARCHAR(100) NOT NULL,
    aggregate_id    VARCHAR(100) NOT NULL,
    event_type      VARCHAR(100) NOT NULL,
    payload         JSONB NOT NULL,
    status          VARCHAR(20) NOT NULL,
    attempts        INTEGER NOT NULL DEFAULT 0,
    next_attempt_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    locked_by       VARCHAR(100),
    locked_at       TIMESTAMPTZ,
    published_at    TIMESTAMPTZ,
    created_at      TIMESTAMPTZ NOT NULL DEFAULT now()
);

CREATE INDEX idx_outbox_ready
    ON outbox_event (status, next_attempt_at, created_at);
```

상태는 최소한 다음처럼 구분합니다.

| 상태 | 의미 | 다음 상태 |
| --- | --- | --- |
| `PENDING` | 아직 발행하지 않았거나 재시도 대기 중입니다. | `PROCESSING`, `FAILED` |
| `PROCESSING` | 한 발행기가 lease를 획득했습니다. | `PUBLISHED`, `PENDING` |
| `PUBLISHED` | Kafka 브로커의 발행 성공 응답을 받았습니다. | 보관 또는 삭제 |
| `FAILED` | 재시도 한도를 초과해 운영자 확인이 필요합니다. | 수동 재처리 |

`PUBLISHED` 행을 즉시 삭제하면 장애 분석과 재발행 판단이 어려워집니다. 보관 기간을
정한 뒤 배치로 삭제하거나, 별도 보관소로 옮기는 정책이 필요합니다. 반대로
`PENDING` 행이 오래 쌓이면 이벤트 발행 지연이므로 모니터링과 알림 대상입니다.

### 주문과 이벤트를 같은 트랜잭션으로 저장하기

주문 상태와 이벤트 payload는 같은 트랜잭션 안에서 만들고, 이벤트 버전을
명시합니다. 아래 코드에서 `OrderCreatedV1`은 Kafka 전송용 DTO이며 JPA 엔티티를
그대로 직렬화하지 않습니다.

```java
public record OrderCreatedV1(
    UUID eventId,
    Long orderId,
    Long customerId,
    BigDecimal totalAmount,
    Instant occurredAt
) {
}

@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final OutboxEventRepository outboxEventRepository;
    private final OrderEventPayloadSerializer payloadSerializer;

    @Transactional
    public Long placeOrder(PlaceOrderCommand command) {
        Order order = Order.createPending(command);
        orderRepository.save(order);

        UUID eventId = UUID.randomUUID();
        OrderCreatedV1 payload = new OrderCreatedV1(
            eventId,
            order.getId(),
            order.getCustomerId(),
            order.getTotalAmount(),
            Instant.now()
        );

        outboxEventRepository.save(OutboxEvent.pending(
            eventId,
            "Order",
            order.getId().toString(),
            "OrderCreated.v1",
            payloadSerializer.serialize(payload)
        ));

        return order.getId();
    }
}
```

`OrderEventPayloadSerializer`는 Jackson의 `JsonProcessingException`을 런타임 예외로
변환해 트랜잭션을 롤백해야 합니다. 직렬화가 실패한 채 주문만 커밋되면 아웃박스의
목적을 잃습니다. 이벤트를 만드는 로직과 주문 저장을 분리된 `REQUIRES_NEW`
트랜잭션으로 두지 않는 이유도 같습니다.

```java
@Component
@RequiredArgsConstructor
public class OrderEventPayloadSerializer {

    private final ObjectMapper objectMapper;

    public String serialize(Object payload) {
        try {
            return objectMapper.writeValueAsString(payload);
        } catch (JsonProcessingException exception) {
            throw new IllegalStateException("이벤트 payload 직렬화에 실패했습니다.", exception);
        }
    }
}
```

### 즉시 확정이 필요한 재고의 예

인기 상품의 재고를 주문 이벤트 소비자가 나중에 차감하도록만 만들면, 동시에 들어온
주문이 재고보다 많이 접수될 수 있습니다. 이 정책을 허용하지 않는다면 주문 생성
트랜잭션에서 조건부 갱신으로 재고 예약을 확정하고, 그 결과를 이벤트로 전파합니다.

```sql
UPDATE inventory
SET available_quantity = available_quantity - :quantity
WHERE product_id = :productId
  AND available_quantity >= :quantity;
```

영향을 받은 행 수가 `1`이면 예약 성공, `0`이면 재고 부족입니다. 이 방식은
"조회 후 Java에서 수량 감소"보다 동시 요청에 안전합니다. 이후 배송·알림·분석 같은
후속 작업은 아웃박스 이벤트로 비동기 처리해도 됩니다.

## 여러 ECS/EKS 인스턴스에서의 발행 동시성

ECS task나 EKS Pod가 여러 개이면 각 인스턴스의 스케줄러가 같은 `PENDING`
이벤트를 동시에 조회할 수 있습니다. 단순한 `SELECT ... WHERE status = 'PENDING'`
뒤 발행은 중복 발행의 원인이 됩니다. 데이터베이스가 공통 조정자 역할을 하도록,
행을 선점(claim)한 뒤에만 발행해야 합니다.

### PostgreSQL `SKIP LOCKED`로 배치 선점하기

아래 쿼리는 잠긴 행을 기다리지 않고 건너뛰므로 여러 발행기 인스턴스가 서로 다른
이벤트 묶음을 가져갈 수 있습니다. 이 문법은 PostgreSQL 기준이며, 사용하는 DB의
잠금 문법과 격리 수준을 확인해야 합니다.

```sql
SELECT id
FROM outbox_event
WHERE (
        status = 'PENDING'
    AND next_attempt_at <= now()
)
OR (
        status = 'PROCESSING'
    AND locked_at < now() - INTERVAL '5 minutes'
)
ORDER BY created_at
FOR UPDATE SKIP LOCKED
LIMIT :batchSize;
```

선점 트랜잭션에서는 선택한 각 행을 `PROCESSING`으로 바꾸고, 인스턴스 식별자와
`locked_at`을 저장한 뒤 즉시 커밋합니다. 발행 작업 전체를 DB 잠금 트랜잭션 안에
두면 Kafka 응답을 기다리는 동안 잠금을 오래 잡으므로 피합니다.

```java
@Service
@RequiredArgsConstructor
public class OutboxClaimService {

    private final JdbcTemplate jdbcTemplate;

    @Transactional
    public List<OutboxMessage> claim(String workerId, int batchSize) {
        List<OutboxMessage> events = jdbcTemplate.query(
            """
            SELECT id, event_id, aggregate_id, event_type, payload
            FROM outbox_event
            WHERE (status = 'PENDING' AND next_attempt_at <= now())
               OR (status = 'PROCESSING'
                   AND locked_at < now() - INTERVAL '5 minutes')
            ORDER BY created_at
            FOR UPDATE SKIP LOCKED
            LIMIT ?
            """,
            new OutboxMessageRowMapper(),
            batchSize
        );

        for (OutboxMessage event : events) {
            jdbcTemplate.update(
                """
                UPDATE outbox_event
                SET status = 'PROCESSING', locked_by = ?, locked_at = now(),
                    attempts = attempts + 1
                WHERE id = ?
                """,
                workerId,
                event.id()
            );
        }
        return events;
    }
}
```

`locked_at`은 lease입니다. 작업자가 발행 중 종료되면 다른 인스턴스가 lease 만료 뒤
해당 행을 다시 선점합니다. lease는 중복을 줄일 뿐, Kafka 발행 성공 응답 직후
프로세스가 종료되는 경우까지 제거하지는 못합니다. 그래서 중복 허용과 소비자
멱등성은 여전히 필수입니다.

### 발행 완료와 재시도 상태를 조건부로 갱신하기

늦게 살아난 이전 작업자가 새 작업자의 상태를 덮어쓰지 않도록, 완료·실패 갱신에는
`locked_by`를 조건으로 넣습니다.

```java
@Repository
@RequiredArgsConstructor
public class OutboxCompletionRepository {

    private final JdbcTemplate jdbcTemplate;

    public boolean markPublished(long id, String workerId) {
        return jdbcTemplate.update(
            """
            UPDATE outbox_event
            SET status = 'PUBLISHED', published_at = now(),
                locked_by = NULL, locked_at = NULL
            WHERE id = ? AND status = 'PROCESSING' AND locked_by = ?
            """,
            id,
            workerId
        ) == 1;
    }

    public void retryLater(long id, String workerId) {
        jdbcTemplate.update(
            """
            UPDATE outbox_event
            SET status = 'PENDING', locked_by = NULL, locked_at = NULL,
                next_attempt_at = now() + INTERVAL '30 seconds'
            WHERE id = ? AND status = 'PROCESSING' AND locked_by = ?
            """,
            id,
            workerId
        );
    }
}
```

운영에서는 고정 30초 대신 지수 백오프, 최대 시도 횟수, 오류 내용, `FAILED` 전이,
수동 재처리 기능을 둡니다. 인스턴스 ID는 Pod 이름이나 ECS task ID처럼 배포마다
구분되는 값으로 만듭니다. ECS와 EKS는 부하에 따라 task 또는 Pod 수를 늘릴 수
있으므로, 스케줄러가 하나만 실행된다는 가정에 의존하면 안 됩니다.

### 순서와 Kafka 확장 단위

Kafka는 토픽 전체의 전역 순서를 보장하지 않습니다. 대신 `orderId`를 메시지 key로
사용하면 같은 주문의 이벤트는 같은 파티션으로 가며, 그 파티션 안에서 순서를
처리할 수 있습니다. Debezium의 Outbox Event Router도 `aggregateid`를 메시지 key로
사용하는 구성을 제공하며, 이를 파티션 내 순서 유지에 사용합니다.

```java
kafkaTemplate.send(
    "commerce.order.events.v1",
    event.aggregateId(), // orderId: 같은 주문은 같은 partition
    event.payload()
);
```

컨슈머 수를 늘려도 한 consumer group 안에서는 파티션 하나를 한 컨슈머만
처리합니다. 따라서 파티션 수보다 많은 컨슈머는 유휴 상태가 됩니다. 반대로 주문별
순서가 중요하다면 같은 주문 이벤트를 서로 다른 key로 보내거나, 같은 주문의 두
이벤트를 서로 다른 발행기가 순서 없이 보내지 않도록 설계하면 안 됩니다. 필요하면
aggregate별 sequence 번호를 이벤트에 넣고, 소비자가 이전 sequence를 확인합니다.

### 소비자의 멱등성: 중복이어도 한 번만 반영하기

Kafka offset 커밋 전 인스턴스가 종료되면 Kafka는 같은 메시지를 다시 전달할 수
있습니다. 소비자의 DB 트랜잭션에서 "이 이벤트를 이미 처리했는가"를 기록하고,
같은 트랜잭션에서 업무 데이터를 변경합니다.

```sql
CREATE TABLE processed_event (
    consumer_name VARCHAR(100) NOT NULL,
    event_id UUID NOT NULL,
    processed_at TIMESTAMPTZ NOT NULL DEFAULT now(),
    PRIMARY KEY (consumer_name, event_id)
);
```

```java
@Component
@RequiredArgsConstructor
public class ShipmentPreparationConsumer {

    private final ProcessedEventRepository processedEventRepository;
    private final ShipmentRepository shipmentRepository;

    @KafkaListener(
        topics = "commerce.order.events.v1",
        groupId = "shipment-service"
    )
    @Transactional
    public void onOrderCreated(OrderCreatedV1 event) {
        boolean firstDelivery = processedEventRepository.insertIfAbsent(
            "shipment-service",
            event.eventId()
        );
        if (!firstDelivery) {
            return;
        }

        shipmentRepository.save(Shipment.preparing(event.orderId()));
    }
}
```

`insertIfAbsent()`는 PostgreSQL이라면 `INSERT ... ON CONFLICT DO NOTHING`으로
구현할 수 있습니다. `processed_event` 삽입과 배송 데이터 저장이 같은 DB
트랜잭션이므로 둘 중 하나만 남지 않습니다. 다만 이 코드는 Kafka offset과 배송 DB를
하나의 전역 트랜잭션으로 묶지는 않습니다. offset 커밋 전 재전달은 중복 처리로
안전하게 무시하는 방식으로 해결합니다.

```java
@Repository
@RequiredArgsConstructor
public class ProcessedEventRepository {

    private final JdbcTemplate jdbcTemplate;

    public boolean insertIfAbsent(String consumerName, UUID eventId) {
        return jdbcTemplate.update(
            """
            INSERT INTO processed_event (consumer_name, event_id)
            VALUES (?, ?)
            ON CONFLICT (consumer_name, event_id) DO NOTHING
            """,
            consumerName,
            eventId
        ) == 1;
    }
}
```

## 발행 방식 선택: 폴링과 CDC

### 애플리케이션 폴링

위 예시처럼 앱이 테이블을 선점해 Kafka에 발행합니다. 구조가 단순하고 상태와
재시도를 앱에서 제어할 수 있습니다. 대신 폴링 지연, lease 회수, 정리 배치를
직접 운영해야 합니다.

### CDC + Debezium

DB 변경 로그에서 outbox `INSERT`를 읽어 Kafka에 전달합니다. 앱의 폴링 코드를
줄이고 DB 변경 순서를 활용할 수 있습니다. 대신 Connector, DB 로그 보존, 스키마
변경을 운영해야 합니다.

Debezium Outbox Event Router는 outbox 테이블의 변경을 캡처해 이벤트로 라우팅하며,
`aggregateid`를 Kafka 메시지 key로 사용할 수 있습니다. CDC를 선택해도 소비자
멱등성과 이벤트 보관·관측은 필요합니다. 어떤 방식을 쓰든 DB 트랜잭션에는 주문과
outbox `INSERT`만 포함한다는 원칙은 같습니다.

## 실무 면접 질문: DB 변경과 Kafka 발행의 정합성

### Transactional Outbox Pattern을 설명해 주세요

Transactional Outbox Pattern은 주문 같은 DB 변경과 이벤트 전송 요청을 같은 DB
트랜잭션으로 저장하는 패턴입니다. 커밋된 아웃박스 레코드는 별도 발행기가 Kafka나
메시지 큐로 전송합니다.

따라서 이 패턴은 "DB 저장"과 "Kafka 발행"을 하나의 트랜잭션으로 묶는 방법이
아닙니다. DB 안에서 원자적으로 처리할 수 있는 범위를 주문 데이터와 전송 대기
레코드까지로 제한하고, Kafka 전송 실패는 재시도로 복구하는 방법입니다.

```text
요청 처리 트랜잭션
  orders INSERT
  outbox_event INSERT (PENDING)
  COMMIT

별도 발행기
  PENDING 이벤트 조회 → Kafka 발행 → 성공 시 PUBLISHED로 변경
```

### 직접 발행하면 생기는 문제

다음처럼 서비스 메서드에서 Kafka를 바로 호출하면 두 시스템의 성공 여부가
엇갈릴 수 있습니다.

```java
@Transactional
public void placeOrder(PlaceOrderCommand command) {
    Order order = orderRepository.save(Order.create(command));
    kafkaTemplate.send("order-created", order.getId().toString());
}
```

| 상황 | 결과 | 문제 |
| --- | --- | --- |
| DB 커밋 성공, Kafka 발행 실패 | 주문만 남습니다. | 후속 서비스가 주문 생성을 알 수 없습니다. |
| Kafka 발행 성공, DB 커밋 실패 | 메시지만 남습니다. | 소비자가 존재하지 않는 주문을 처리할 수 있습니다. |

`@Transactional`은 일반적으로 연결된 DB 트랜잭션을 제어할 뿐입니다. Kafka 전송
성공과 DB 커밋을 자동으로 하나의 원자적 작업으로 만들지 않습니다.

### 주문과 아웃박스를 함께 저장하는 예시

아웃박스 이벤트에는 중복 제거에 사용할 이벤트 ID, 이벤트 종류, 발행할 내용,
발행 상태를 저장합니다. 예시의 JSON 문자열은 설명을 단순화하기 위한 것이며,
운영에서는 이벤트 스키마와 버전 정책을 별도로 관리해야 합니다.

```java
@Service
@RequiredArgsConstructor
public class OrderService {

    private final OrderRepository orderRepository;
    private final OutboxEventRepository outboxEventRepository;

    @Transactional
    public Long placeOrder(PlaceOrderCommand command) {
        Order order = orderRepository.save(Order.create(command));

        OutboxEvent event = OutboxEvent.pending(
            UUID.randomUUID(),
            "Order",
            order.getId(),
            "OrderCreated",
            "{\"orderId\": " + order.getId() + "}"
        );
        outboxEventRepository.save(event);

        return order.getId();
    }
}
```

주문 저장이 실패하면 아웃박스 이벤트도 함께 롤백됩니다. 반대로 주문이 커밋되면
발행 대기 이벤트도 반드시 남습니다. Kafka가 일시적으로 장애여도 DB의
`PENDING` 레코드를 다시 읽어 재시도할 수 있습니다.

### 여러 인스턴스에서 사용하는 발행기 예시

발행기는 주기적으로 미발행 이벤트를 가져와 Kafka 전송 성공 확인 뒤 상태를
변경합니다. 아래 예시는 앞에서 설명한 `SKIP LOCKED` 기반 선점과 lease 회수
방식을 연결한 형태입니다. `WorkerIdProvider`는 Pod 이름이나 ECS task ID처럼
실행 인스턴스를 구분하는 값을 돌려준다고 가정합니다.

```java
@Component
@RequiredArgsConstructor
public class OutboxPublisher {

    private final OutboxClaimService outboxClaimService;
    private final OutboxCompletionRepository outboxCompletionRepository;
    private final WorkerIdProvider workerIdProvider;
    private final KafkaTemplate<String, String> kafkaTemplate;

    @Scheduled(fixedDelay = 1_000)
    public void publishPendingEvents() {
        String workerId = workerIdProvider.workerId();
        List<OutboxMessage> events = outboxClaimService.claim(workerId, 100);

        for (OutboxMessage event : events) {
            try {
                kafkaTemplate.send(
                    "commerce.order.events.v1",
                    event.aggregateId(),
                    event.payload()
                ).get();
                outboxCompletionRepository.markPublished(event.id(), workerId);
            } catch (Exception exception) {
                outboxCompletionRepository.retryLater(event.id(), workerId);
            }
        }
    }
}
```

Kafka가 메시지를 받은 직후 애플리케이션이 종료되면, `PUBLISHED` 상태 갱신 전에
같은 이벤트가 다시 발행될 수 있습니다. 그러므로 아웃박스는 보통 적어도 한 번
전달(at-least-once)을 목표로 합니다. 소비자는 이벤트 ID를 저장하거나 업무 키에
유니크 제약 조건을 적용해 중복 이벤트를 안전하게 무시해야 합니다.

### 면접에서 확인하는 지점

면접에서는 "Kafka를 사용했다"보다 실패 시나리오를 어떻게 복구하는지 설명하는
것이 중요합니다. 다음처럼 답할 수 있습니다.

> 주문 데이터와 아웃박스 이벤트를 같은 DB 트랜잭션으로 저장했습니다. DB 커밋이
> 성공하면 전송 대기 이벤트가 남으므로, Kafka 발행 실패는 재시도로 복구할 수
> 있습니다. 발행 성공 직후 상태 갱신 전에 장애가 나면 중복 발행될 수 있으므로,
> 소비자는 이벤트 ID 기준으로 멱등하게 처리했습니다. DB와 Kafka의 전역 원자성을
> 전제로 두지 않고, 최종적 일관성과 재처리 가능한 구조를 선택했습니다.

DB와 Kafka를 분산 트랜잭션으로 묶는 선택지도 이론적으로는 있을 수 있지만, 두
시스템의 지원 범위, 장애 복구, 운영 복잡도가 커집니다. 특히 Kafka 프로듀서
트랜잭션은 Kafka 내부의 원자성을 제공하는 기능이지, 일반 관계형 DB까지 자동으로
포함하지는 않습니다. 그래서 대부분의 서비스 간 이벤트 발행에는 아웃박스와 소비자
멱등성 조합을 우선 검토합니다.
