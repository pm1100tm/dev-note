# 연관관계 고급 & N+1 문제

연관관계를 매핑하면 `member.getOrders()`처럼 회원의 주문을 객체로 탐색할 수
있습니다. 하지만 연관 데이터를 언제, 몇 번 가져오는지 고려하지 않으면 요청 하나가
수백 개의 SQL로 늘어날 수 있습니다. 이 대표적인 문제가 N+1입니다.

이 문서에서는 `Member`와 `Order` 관계를 기준으로 조회 범위를 설계하고, 연관관계의
생명주기를 함께 관리할 때 필요한 선택 기준을 설명합니다.

## Member와 Order 관계

회원 한 명이 여러 주문을 가질 수 있으므로 `Order` 테이블에 `member_id` 외래 키를
둡니다. 외래 키를 가진 `Order`의 `member`가 관계의 주인입니다. `Order`는 SQL에서
예약어로 해석될 가능성을 피하려고 실제 테이블 이름을 `orders`로 명시하는 편이
안전합니다.

```java
@Entity
@Table(name = "orders")
public class Order {

    @ManyToOne(fetch = FetchType.LAZY, optional = false)
    @JoinColumn(name = "member_id", nullable = false)
    private Member member;
}
```

`Member`에서 주문 목록을 탐색해야 한다면 반대쪽을 다음처럼 선언합니다.

```java
@OneToMany(mappedBy = "member", fetch = FetchType.LAZY)
private List<Order> orders = new ArrayList<>();
```

`mappedBy = "member"`는 `Order.member`가 외래 키를 관리한다는 뜻입니다. 따라서
회원의 주문 목록을 조회하는 것과 주문의 회원을 변경하는 것은 서로 다른 작업이며,
어느 쪽을 변경할지 코드에서 분명히 해야 합니다.

## N+1 문제가 생기는 과정

회원 목록을 조회한 뒤 각 회원의 주문 목록을 화면에 보여 주는 상황을 생각해
보겠습니다. 회원을 3명 조회했는데 주문 목록을 사용할 때마다 추가 조회가 실행되면
SQL은 다음처럼 실행될 수 있습니다.

```java
public interface MemberRepository extends JpaRepository<Member, Long> {
}

List<Member> members = memberRepository.findAll();

for (Member member : members) {
    member.getOrders().size();
}
```

```sql
-- 회원 목록을 조회하는 1번의 SQL입니다.
select * from members;

-- 회원마다 주문을 조회하는 N번의 SQL입니다.
select * from orders where member_id = 1;
select * from orders where member_id = 2;
select * from orders where member_id = 3;
-- ... 주문 수만큼 반복!
-- 100개 주문 조회 시: 1 + 100 = 101개 쿼리 실행!
```

처음 조회한 회원 수가 N이고, 주문 컬렉션을 읽을 때 추가 SQL이 N번 실행되어
N+1이라고 부릅니다. 회원이 3명일 때는 작아 보이지만, 운영 데이터가 수백 명이면
DB 왕복도 수백 번이 됩니다.

### 확인 방법

N+1은 코드만 보고 단정하지 말고 실제 SQL 로그와 조회 건수를 확인해야 합니다.
개발 환경에서 Hibernate SQL 로그를 켜고 다음을 함께 살펴봅니다.

- API 한 번의 요청에서 실행된 SQL 개수입니다.
- 같은 형태의 SELECT가 반복되는지 여부입니다.
- SQL 실행 시간과 반환 행 수입니다.
- 조회 결과를 엔티티로 만들 때 불필요한 컬럼까지 읽는지 여부입니다.

## 잘못된 해결: EAGER로 바꾸기

```java
@OneToMany(fetch = FetchType.EAGER, mappedBy = "member")
private List<Order> orders = new ArrayList<>();
```

`EAGER`로 바꾸면 항상 JOIN 한 번으로 해결된다고 생각하기 쉽습니다. 그러나 JPA는
연관 데이터를 반드시 즉시 준비하라고 요구할 뿐, Hibernate가 항상 하나의 JOIN SQL을
사용하도록 보장하지 않습니다. 주문을 조회하지 않아도 되는 화면까지 주문을 가져오게
되어 다른 API에서 오히려 성능이 나빠질 수 있습니다.

`EAGER`를 전역적인 N+1 해결책으로 사용하지 말고, 조회 목적마다 필요한 데이터를
명시적으로 선택합니다. `@ManyToOne`의 JPA 기본값은 `EAGER`이므로 기본 매핑에서
`LAZY`를 명시하는 습관도 중요합니다. `LAZY` 역시 구현체에 따라 동작 방식이 달라질
수 있는 힌트이며, N+1을 자동으로 없애 주지는 않습니다.

## Fetch Join으로 한 번에 조회하기

이번 조회에서 회원과 주문이 모두 필요하다면 JPQL의 fetch join을 사용할 수 있습니다.

```java
public interface MemberRepository extends JpaRepository<Member, Long> {

    @Query("select distinct m from Member m left join fetch m.orders")
    List<Member> findMembersWithOrders();
}

List<Member> members = memberRepository.findMembersWithOrders();
```

Spring Data JPA의 `@Query`에 작성한 `left join fetch`는 회원을 조회하면서 주문도
같은 조회에서 가져오도록 요청합니다.
`distinct`는 한 회원에 주문이 여러 개일 때 JOIN 결과에서 같은 회원이 반복되는
문제를 객체 결과에서 줄이는 데 사용합니다. 생성되는 SQL의 형태와 중복 제거 방식은
JPA 구현체와 버전에 따라 다를 수 있으므로 SQL 로그를 확인해야 합니다.

### 잘못된 예: 모든 조회에 fetch join 적용하기

```java
@Query("select distinct m from Member m left join fetch m.orders")
List<Member> findAll();
```

회원 목록만 필요한 화면에서도 항상 주문 전체를 가져오게 됩니다. 주문이 많은 회원이
포함되면 반환 행과 메모리 사용량이 급증할 수 있습니다. 조회 결과에 주문이 필요한
유스케이스만 별도 메서드로 분리하는 편이 안전합니다.

### 올바른 예: 조회 목적을 메서드 이름에 드러내기

```java
@Query("select distinct m from Member m left join fetch m.orders")
List<Member> findMembersWithOrders();
```

`findMembersWithOrders()`는 주문까지 필요하다는 의도를 코드에 남깁니다. 기본 목록
조회와 주문 포함 조회를 나누면 각 화면에 필요한 데이터만 가져올 수 있습니다.

## 컬렉션 조회와 페이징

**컬렉션 fetch join은 페이징과 함께 사용할 때 특히 주의**해야 합니다. 회원 하나가 주문
여러 행으로 펼쳐지므로 DB가 JOIN 결과에 먼저 `limit`을 적용하면 회원 단위 페이지가
정확하지 않을 수 있습니다. Hibernate는 설정이나 버전에 따라 메모리에서 페이징하거나
경고를 출력할 수 있으므로, 대량 데이터에서는 이 조합을 그대로 사용하지 않습니다.

### 컬렉션 Fetch Join + 페이징 금지!

컬렉션 Fetch Join과 페이징을 함께 사용하면 메모리에서 페이징합니다.

해결책: @BatchSize 또는 별도 쿼리로 분리

- 1. 둘 이상의 컬렉션 Fetch Join 불가
  - 카테시안 곱으로 데이터 폭발. MultipleBagFetchException 발생
- 2. 컬렉션 Fetch Join + 페이징 불가
  - 메모리에서 페이징하여 OutOfMemoryError 위험
- 3. 별칭(alias) 사용 제한
  - Fetch Join 대상에 별칭을 주고 WHERE 조건 사용 비권장

**Fetch Join 사용 가이드**

- @ManyToOne, @OneToOne: Fetch Join 자유롭게 사용
- @OneToMany: 하나만 Fetch Join, DISTINCT 필수
- 페이징 필요 시: @BatchSize 또는 별도 쿼리 사용
- 복잡한 경우: DTO 직접 조회 고려

### 실무에서는 다음처럼 두 단계로 나누는 방법을 고려합니다.

- 먼저 회원 ID만 페이지 단위로 조회합니다.
- 조회한 ID로 회원과 주문을 별도의 fetch join 또는 배치 조회로 가져옵니다.
- 최종 결과를 ID 순서에 맞게 조합하고 필요한 DTO로 변환합니다.

단일 값 연관관계인 `Order -> Member` fetch join은 컬렉션보다 페이징 제약이 적지만,
결과 데이터와 인덱스가 적절한지는 항상 실제 실행 계획으로 확인해야 합니다.

## EntityGraph와 배치 조회

조회 메서드마다 JPQL을 직접 작성하기 어렵다면 EntityGraph로 이번 조회에서 필요한
연관관계를 선언할 수 있습니다. 다음 예시는 Spring Data JPA에서 사용하는 형태이며,
구체적인 repository 문법은 다음 학습 주제에서 자세히 다룹니다.

```java
@EntityGraph(attributePaths = "orders")
@Query("select m from Member m")
List<Member> findMembersWithOrders();
```

EntityGraph는 조회 작업의 fetch 범위를 정의하는 표준 기능입니다. `fetchgraph`와
`loadgraph`의 의미, 중첩된 속성 처리 방식은 JPA와 구현체 설정을 확인해야 합니다.

연관 객체를 꼭 한 번의 JOIN으로 가져오지 않아도 된다면 Hibernate의 배치 조회를
사용할 수 있습니다.

```java
@BatchSize(size = 100)
@OneToMany(mappedBy = "member", fetch = FetchType.LAZY)
private List<Order> orders = new ArrayList<>();
```

`@BatchSize`는 JPA 표준이 아니라 Hibernate 기능입니다. Hibernate가 여러 회원의
주문 컬렉션을 필요로 할 때 ID를 묶어 `IN` 조건으로 조회하도록 도울 수 있지만,
정확한 SQL 개수와 묶음 크기는 데이터와 설정에 따라 달라집니다. 이 기능을 사용하면
다른 JPA 구현체로 바꿀 때 대체 설정이 필요합니다.

## Cascade와 orphanRemoval

Cascade와 fetch는 서로 다른 기능입니다. fetch는 언제 조회할지 정하고, cascade는
부모 엔티티에 수행한 생명주기 작업을 연관 엔티티에도 전파할지 정합니다.

```java
@OneToMany(
    mappedBy = "member",
    cascade = CascadeType.ALL,
    orphanRemoval = true
)
private List<Order> orders = new ArrayList<>();
```

`CascadeType.ALL`을 사용하면 회원을 저장하거나 삭제할 때 주문에도 같은 작업이
전파될 수 있습니다. `orphanRemoval = true`는 회원의 주문 컬렉션에서 주문을 제거했을
때 그 주문 행도 삭제하도록 요청합니다.

### 잘못된 예: 모든 연관관계에 `CascadeType.ALL` 적용하기

```java
@ManyToMany(cascade = CascadeType.ALL)
private Set<Member> members = new HashSet<>();
```

회원처럼 여러 곳에서 공유될 수 있는 엔티티를 한 관계의 삭제와 함께 삭제하면 다른
관계까지 영향을 받을 수 있습니다. cascade는 부모가 자식의 생명주기를 실제로
소유할 때만 제한적으로 사용합니다.

`orphanRemoval`은 고아가 된 자식을 삭제하는 기능이지, 외래 키를 NULL로 바꾸는
기능이 아닙니다. 공유 엔티티나 삭제 이력이 필요한 데이터에는 신중하게 적용하고,
업무상 삭제 대신 상태 변경이 필요하다면 명시적인 상태 필드를 사용합니다.

## 실무 조회 기준

- 연관관계 어노테이션의 fetch 값을 바꾸기 전에 API의 조회 목적을 정합니다.
- N+1은 SQL 로그와 실행 횟수로 확인하고, 단순히 `EAGER`로 바꾸지 않습니다.
- 필요한 주문 데이터만 fetch join, EntityGraph, 배치 조회 중 하나로 선택합니다.
- 컬렉션 fetch join과 페이징을 함께 사용할 때는 두 단계 조회를 우선 검토합니다.
- 조회 결과는 엔티티를 그대로 반환하지 않고, 필요한 필드만 DTO로 변환합니다.
- cascade와 orphanRemoval은 회원이 주문을 소유하는지 확인한 뒤 적용합니다.
- Hibernate 전용 기능을 사용하면 구현체 종속성과 버전별 동작을 기록합니다.

성능 개선의 목표는 SQL 개수를 무조건 1개로 만드는 것이 아닙니다. 화면이나 API가
필요로 하는 데이터만 안정적인 쿼리와 메모리 사용량으로 가져오는 것이 목표입니다.
