# 디자인 시스템 설계와 운영

디자인 시스템은 제품 경험을 구성하는 공통 규칙과 구현 자산의 집합이다. UI를 빠르게 복제하는
것이 목적이 아니라, 일관성·접근성·변경 비용을 함께 관리하는 것이 목적이다.

## 구성 요소

- 디자인 토큰: 색상, 타이포그래피, 간격, 그림자, 반경처럼 반복되는 값을 의미 단위로 정의한다.
- 컴포넌트: Button, Input, Dialog처럼 재사용하는 UI와 상태·동작·접근성 계약을 제공한다.
- 패턴: 폼 검증, 빈 상태, 오류 처리처럼 여러 컴포넌트를 조합하는 사용 방법을 정의한다.
- 문서와 도구: 사용 예시, 변경 이력, Figma 라이브러리, 코드 패키지를 연결한다.

## 토큰 설계

원시값보다 의미 토큰을 먼저 사용하면 브랜드 변경과 다크 모드 적용 범위를 줄일 수 있다.

```css
:root {
  --color-blue-600: #2563eb;
  --color-text-primary: #111827;
  --color-action-primary: var(--color-blue-600);
  --space-2: 0.5rem;
  --space-4: 1rem;
}
```

- `--color-blue-600`은 원시 토큰이고, `--color-action-primary`는 용도를 나타내는 의미 토큰이다.
- 컴포넌트는 원시 색상 대신 의미 토큰을 사용한다.
- 명명 규칙, 단위, 다크 모드 전환 규칙을 토큰 문서에 함께 기록한다.

## 컴포넌트 계약

컴포넌트는 모양뿐 아니라 상태와 접근성 동작을 API로 제공해야 한다.

| 항목 | 확인할 내용 |
| --- | --- |
| 상태 | default, hover, focus, disabled, loading, error 상태를 정의한다. |
| 접근성 | 키보드 조작, focus 표시, 이름, 역할, 색 대비를 검증한다. |
| API | variant, size, disabled처럼 필요한 속성만 노출한다. |
| 확장 | 임의 CSS override보다 slot, composition, token을 우선 제공한다. |

예를 들어 버튼의 `disabled` 상태는 색상만 바꾸는 것이 아니라 클릭·키보드 이벤트를 막고,
보조기술에 상태를 전달해야 한다. 로딩 상태에서는 중복 제출을 막는 정책도 함께 정한다.

## 접근성 기준

- 텍스트와 배경의 색 대비는 일반 텍스트 기준 WCAG AA 4.5:1 이상을 목표로 한다.
- 마우스 없이 모든 주요 흐름을 키보드로 완료할 수 있어야 한다.
- focus outline을 제거하지 말고, 배경과 구분되는 focus 스타일을 제공한다.
- 아이콘만 있는 버튼에는 접근 가능한 이름(`aria-label` 등)을 제공한다.
- 오류 메시지는 색상만으로 표현하지 않고 텍스트와 적절한 연결 관계를 함께 제공한다.

## 운영과 버전 관리

- 컴포넌트 변경은 breaking change 여부를 판단해 semantic versioning으로 배포한다.
- deprecated API에는 마이그레이션 방법과 제거 예정 버전을 문서화한다.
- Storybook, 시각 회귀 테스트, 접근성 테스트를 CI에 연결해 회귀를 줄인다.
- 디자인과 개발의 소유자·리뷰 기준·릴리스 절차를 명확히 정한다.
