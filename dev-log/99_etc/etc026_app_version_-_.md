# 앱 버전 정보의 의미

애플리케이션의 버전 정보는 보통 아래와 같은 형식이 됩니다.

```shell
1.0.5 (6)
```

1.0.5 (6)의 의미는 보통 이렇게 봅니다.

```shell
1.0.5 (6)
│ │ │ │
│ │ │ └─ versionCode / build number
│ │ └──── patch
│ └────── minor
└──────── major
```

- 1: major 버전
  - 큰 기능 변경, 구조 변경, 호환성에 영향이 큰 변경 때 올립니다.

- 0: minor 버전
  - 기능 추가는 있지만 기존 사용 흐름과 호환되는 변경 때 올립니다.

- 5: patch 버전
  - 버그 수정, 작은 개선, 안정화 배포 때 올립니다.

- (6): Android 기준 versionCode
  - Google Play와 Android 시스템이 앱 업데이트 여부를 판단하는 정수입니다.
  - 같은 패키지명에서는 새 배포의 versionCode가 기존 설치본보다 반드시 커야 합니다.
  - 사용자에게 보이는 버전명은 1.0.5이고, (6)은 내부 빌드 번호에 가깝습니다.

만약 코드 수정만 있고 사용자에게 보여줄 버전명은 유지하려면:

```shell
ANDROID_VERSION_NAME=1.0.5
ANDROID_VERSION_CODE=7
```

## 각 자리수의 최대 값이 있는가?

실무 기준으로는 이렇게 보면 됩니다.

versionName = 1.0.5의 각 자리수에는 Android/iOS가 강제하는 최대값은 사실상 없습니다. 문자열입니다.

```
1.0.5
│ │ │
│ │ └─ patch
│ └─── minor
└───── major
```

- major, minor, patch는 팀 규칙입니다.
- 보통은 숫자로 관리하지만 1.0.999, 2.15.37 같은 것도 가능합니다.
- 다만 스토어, 배포 문서, 사용자 안내를 생각하면 너무 큰 숫자는 피하는 게 좋습니다.

반면 (6)에 해당하는 versionCode / build number는 제한이 있습니다.

```
Android versionCode:

최대값: 2100000000
Google Play 기준으로 versionCode는 양의 정수이고, 새 버전은 이전보다 반드시 커야 합니다.
```

```
iOS CFBundleVersion:

일반적으로 숫자와 점 조합 사용
예: 6, 7, 1.0.5, 100
```

App Store Connect에서는 이전 빌드보다 증가해야 합니다.

이 프로젝트에서는 현재 IOS_VERSION_CODE=6처럼 단일 정수로 쓰고 있으므로 Android처럼,
계속 7, 8, 9 식으로 올리는 게 가장 단순합니다.

권장 규칙은 이겁니다.

```
ANDROID_VERSION_NAME=1.0.5
ANDROID_VERSION_CODE=7

IOS_VERSION_NAME=1.0.5
IOS_VERSION_CODE=7
```

- 사용자에게 보이는 변경이 없고 재배포만 필요하면 VERSION_CODE만 증가
- 기능 추가나 사용자에게 보이는 변화가 있으면 VERSION_NAME도 증가
- VERSION_CODE는 절대 감소시키지 않기

### 그러면 1.0.5 (6) 에서 1.0.6 (6) 으로 올리는게 가능한가?

가능은 합니다. 하지만 Android/iOS 배포 기준으로는 권장하지 않습니다.

```
1.0.5 (6) → 1.0.6 (6)
```

의미는:

- versionName: 1.0.5 → 1.0.6
- versionCode: 6 유지

즉, 사용자에게 보이는 버전명만 올라가고 내부 빌드 번호는 그대로입니다.

문제는 스토어/기기 업데이트 판단입니다.

Android는 versionCode가 이전 설치본보다 커야 업데이트로 인정됩니다. 이미 versionCode=6인 앱이
설치되어 있다면, 1.0.6 (6) APK/AAB는 새 버전으로 설치/업데이트되지 않을 수 있습니다.

iOS도 App Store Connect/TestFlight/MDM 배포에서 빌드 번호인 CFBundleVersion이 증가해야
하는 흐름이 일반적입니다. 같은 빌드 번호 6으로 다시 올리면 거부되거나 기존 빌드와 충돌할 수 있습니다.

따라서 실제 배포라면 이렇게 올리는 게 맞습니다.

```
1.0.5 (6) → 1.0.6 (7)
```

## 그러면 1.0.5 (6) 에서 1.0.5 (7) 으로 올리는게 가능한가?

가능합니다. 그리고 실제 배포에서는 이 방식이 자주 쓰입니다.

```
1.0.5 (6) → 1.0.5 (7)
```

의미는:

```
versionName: 1.0.5 유지
versionCode: 6 → 7 증가
```

즉, 사용자에게 보이는 앱 버전은 1.0.5 그대로 두고, 내부 빌드 번호만 올리는 것입니다.

이런 경우에 적합합니다.

- 같은 1.0.5 버전의 재빌드
- 사소한 수정
- 인증서/설정/웹뷰 껍데기 수정
- 스토어 또는 MDM에 새 파일을 다시 올려야 하는 경우
- 사용자는 같은 앱 버전으로 보게 하고 싶지만, 기기는 업데이트로 인식해야 하는 경우
